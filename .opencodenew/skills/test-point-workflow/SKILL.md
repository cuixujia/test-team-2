# 测试点生成与清单规范

功能点拆分、命名、颗粒度、模板库与生成流程以 `test-knowledge-canon`《测试点生成指南》二至六章为权威，本文不重复；本文承载产物清单规则与原文未覆盖的生成细则。

## 生成规则

### 依据类型与生成红线

- `原文依据`：验证方向与判定内容由 `出处锚点` 或澄清答复直接推导。
- `方法论补充`：资料只写了功能/对象，没描述某个测试维度、所属小类或该小类的关注点，而四份原文知识链里有 → 按该关注点发散补测试点，用来提高覆盖率。
- 五条红线，违反即虚构，QA 判阻塞：
  1. 验证对象须有原文对象锚点；原文没有的字段、功能、状态、角色，不得生成对应 TP。
  2. 不得补造流程、权限、结果、状态流转等业务规则与提示文案；资料未描述的内容不得虚构为已描述。
  3. 无具体依据支撑的内容只写宽泛表述，如 测试姓名字段最大长度、验证超长输入被拦截，不写死具体数值、阈值、枚举值、文案。
  4. 具体取值须以澄清答复为依据，`澄清依据` 标对应 C 编号；无澄清依据写 `-`。
  5. 两类 TP 都必须带 `出处锚点`；不新增原文没有的对象，不补造业务规则。

### 条目与命名细则

- 查询/筛选类：并列且未规定不同规则的查询项合成一条 TP，`用例展开重点` 逐项点名，如 `按名称筛选 ;; 按编号筛选 ;; 按状态筛选`，项数即查询项数，逐项覆盖实现在 TC 层；PRD 对不同查询项明文规定不同结果、规则、权限的按拆分规则拆，不为省条数硬塞。
- 描述不清：PRD 未说明并列条件是否存在不同规则 → 先按同一目标合并成一条，模糊点不得自行补造规则。
- 并列双结果谓词：名称以「并/且」串联两个结果时自查，两结果出自同一套自动留存处理可合，PRD 规定了不同规则则拆。
- 验证词去重：名内「验证」仅出现一次，「验证XX功能验证」式词面重复判错。
- 过粗校正例外：「验证XX功能」式仅当该 TP 的直属 TC 承载两类及以上判定维度时判合规，否则拆分或判过粗；PRD 原词照抄场景不因词面命中而判错。

### 排序规则

- `关联业务功能` 相同的 TP 排在一起，中间不插别的功能；段先后按 scope 选中项顺序，不许 F01 → F02 → 又回 F01。
- 段内先写该功能的全部功能级 TP，同层按 正向 → 核心逻辑与状态 → 异常处理 → 边界与数据校验 → 其他 排列；再把该功能的场景级 TP 放在这一段最后，不集中放到整张清单最末。
- 场景级 TP 按流程起点或主要承载功能归属放进那一段，归属拿不准时查主件的功能归属说明。排序须人工逐行核对，不进机验。

## 清单结构

### 落盘模板

文件骨架：

```markdown
# 测试点清单

| 编号 | 关联业务功能 | 测试点名称 | 类型 | 测试维度 | 所属小类 | 用例展开重点 | 依据类型 | 澄清依据 | 出处锚点 |
|---|---|---|---|---|---|---|---|---|---|
| TP-001 | F01 需求新增 | 验证新增界面展示正确性 | 功能级 | 基础功能 | 功能正确性 | UI：页面布局 ;; 元素可见性 | 原文依据 | - | prd1.md:5 => "系统支持新增个人客户与对公客户" |
| TP-002 | F01 需求新增 | 验证正常输入新增功能正确性 | 功能级 | 基础功能 | 功能正确性 | 正向主流程 ;; 数据落库 ;; 状态变更 | 原文依据 | C-01 | prd1.md:15 => "保存成功后状态置为待审核" |
| TP-003 | F01 需求新增 | 验证新增输入域长度与字符约束 | 功能级 | 基础功能 | 字段校验 | 姓名最大长度 ;; 姓名特殊字符与空格 ;; 年龄数值精度 | 方法论补充 | - | prd1.md:8 => "表单字段：姓名、年龄" |
| TP-004 | F01 需求新增 | 验证新增-审核-推送完整流程 | 场景级 | 业务流程 | 主流程 | 基本流正向贯通 ;; 环节失败备选流 | 原文依据 | C-02(默认) | prd1.md:20 => "审核通过后触发推送" |
```

### 字段要求

| 字段 | 要求 |
|---|---|
| 编号 | `TP-001` 三位数字起步；重排后必须重编号，连续无跳号；机验正则 `TP-\d+` |
| 关联业务功能 | scope 选中功能，第一个空格分隔 F 编号与 PRD 原文名称，如 `F01 需求新增`；禁自创模块词；TC 侧须逐字一致 |
| 测试点名称 | 短语级 ≤30 字，PRD 叫法照抄，禁结果词、处理逻辑、具体值、并列双结果谓词，`验证` 仅一次 |
| 类型 | 仅 `功能级` / `场景级`；按验证范围分型：单功能点内为功能级，跨功能点链路为场景级；性能、安全等非功能维度适用同一标尺 |
| 测试维度 | 单值，取维度选型圈定组合中的测试维度层，值域为《测试维度定义》「一、大类与测试维度总览」十枚举之一 |
| 所属小类 | 单值，该 TP 主要承载的小类；必须属于所选维度下《测试维度定义》「二、测试维度明细」合法小类集，维度-小类组合走机验。小类级覆盖 = 本轮选型圈定的每个小类在 `所属小类` 列至少有 1 条 TP 对应，人工对表，缺失判阻塞 |
| 用例展开重点 | 短语级，建议 2~3 项以上，` ;; ` 分隔；每项须是一个可独立判定的展开分支，按 PRD 客观计数枚举。字段校验的约束 = 原文已给约束 + 《测试维度定义》「二、测试维度明细」1.2「字段校验」关注点 + 《通用测试规则》「1. 基础功能」1.2「字段校验（输入域测试）」六大固定场景发散的约束，后者同样计入 N。禁止把通则写成项——「每项至少 1 条用例」「覆盖正向反向」类元描述不计入 N。来源 = 《测试点生成指南》「五、典型测试点模板库」右列 + 《通用测试规则》对应维度关注点裁剪，供 TC 展开直接消费；项数 N 仅作展开充分性人工建议，机验只校非空 |
| 依据类型 | 仅 `原文依据` / `方法论补充`，单值非空 |
| 澄清依据 | 无写 `-`；有写 `C-编号` 或 `C-编号(默认)`，多值 ` ;; ` 分隔；编号必须存在于 `state/clarifications.md`；无澄清依据的方法论补充条目写 `-`，有澄清答复的具体值标对应 C 编号 |
| 出处锚点 | 至少 1 条、一般 1~3 条 |
| 通用书写 | 单元格内换行用 `<br>`，禁止真实换行；多值项为锚点、澄清依据、用例展开重点 |

# 引文机验与产物格式契约（citation-verify）

## 锚点口径（TP / TC / clarifications / resources-index 四类产物通用）

| 原文类型 | 锚点格式 | 例 |
|---|---|---|
| md/txt/csv | `文件名:起始行[-结束行] => "摘抄"` | `prd1.md:12-15 => "客户名称长度不超过50个字符"` |
| docx | `文件名#章节标题 => "摘抄"` | `需求.docx#新增客户 => "保存成功后状态置为待审核"` |
| xlsx | `文件名#Sheet名!单元格 => "摘抄"` | `规则.xlsx#字段规则!B3 => "证件号为必填项"` |

规则：

1. 格式：`文件名:行号 => "摘抄"`；多锚点写同一单元格用 ` ;; ` 分隔；单元格内容禁止出现 `|`（拆断列，机验判格式非法）。
2. 摘抄从原文照抄、≤50 字（不含结尾截断符）、须为定位行的**连续原文片段**（可去表格竖线压缩）；超出截断并以 `...` 结尾；禁止改写、缩合、空格补齐。
3. 摘抄内禁止半角双引号（原文如有换全角 `”`）、禁止 `|`、禁止 ` => `（无法避让时换选摘抄片段）。
4. 禁止裸格式 `文件名:行号`（无摘抄段）。
5. 横线/分隔符一律 ASCII 短横线 `-`；长横线 `—` 会被机验拒收（澄清依据列尤其注意）。
6. docx 章节标题须对应原文的 Heading 样式段落（标题可只写核心词，允许包含匹配）；xlsx 单元格坐标形如 `B3`（单格）；docx/xlsx 不转 md，机验现场抽取、用完即弃。
7. 两类 `依据类型` 都必须带锚点，锚点逐条机验真实性：`原文依据` 的锚点须能支撑该条目的判定性内容；`方法论补充` 的锚点用于证明**验证对象（字段/功能/状态/角色）在原文中存在**（对象锚点），不要求支撑按方法论补充的约束类型。**原文没有的对象一律不得生成对应测试内容**——这是方法论补充不变成虚构的机器底线。

## 清单表机器契约（列名与脚本 *_REQUIRED 逐字一致）

**TP 表 10 列**（`TP_REQUIRED`）：`编号 | 关联业务功能 | 测试点名称 | 类型 | 测试维度 | 所属小类 | 用例展开重点 | 依据类型 | 澄清依据 | 出处锚点`，取值详表见 `test-point-workflow`。`关联业务功能` 格式=第一个空格分隔 F 编号与名称（如 `F01 需求新增`）。机验除表面格式外另校值域：`类型` ∈ {功能级, 场景级}；`测试维度` ∈《测试维度定义》§一十枚举、`所属小类` ∈ 所选维度下 §二合法小类集（组合合法性，均单值）；`用例展开重点` 非空；`依据类型` ∈ {原文依据, 方法论补充}，单值非空。**项数不作机验下限（机验只校 M≥2），人工判据为逐 TP `M≥N`、`M<N` 判展开不足（N 核算口径见 `test-point-workflow`「落盘模板」与 `test-case-workflow`「展开数量守恒」）**。小类级覆盖不做机验（无基线产物），由人工对表（见 `test-point-workflow` 质检判据 5）。

**TC 表 13 列**（`TC_REQUIRED`）：`编号 | 关联业务功能 | 关联TP | 用例名称 | 用例类型 | 测试方法 | 前置条件 | 测试数据 | 操作步骤 | 预期结果 | 依据类型 | 澄清依据 | 出处锚点`，取值详表见 `test-case-workflow`。机验除表面格式外另校：`测试方法` ∈ 六枚举（等价类+边界值/决策表/状态迁移/场景法/正交实验/错误推测）；`依据类型` ∈ {原文依据, 方法论补充}，单值非空；`关联TP` 双段（第一个空格分隔）：编号段 `TP-\d+` 且存在于 TP 清单、**名称段与 TP 清单该 TP 的 `测试点名称` 逐字一致**；`关联业务功能` 逐字等于其主 TP 的 `关联业务功能`（join 一致性）；**数量守恒**（`--tp` 与 `--tc` 同参时生效）：逐 TP 统计直属 TC 数 M，`M≥1` 且 `<2` 判 failures；**`M=0` 跳过判定，由覆盖缺口 warning 承载并须书面理由记 `state.md`，作为 `M≥2` 下限的例外**；`M≥2` 通过。

**依据类型二分（TP/TC 通用，`BASIS_TYPES`）**：`原文依据` = 测试内容（含判定性内容）由 `出处锚点` 或澄清答复直接推导；`方法论补充` = 资料未描述、由模型自由发挥补出的测试内容，发散依据为四份原文知识链（②§二 关注点 / ③对应章节测试项 / ④§五 模板库 / ①§七 方法选型）或测试经验判断的应测点。**阶段 2 选静默生成的缺口、以及任何自由发挥生成的 TP/TC 一律标 `方法论补充`；选补充资料后按答复写出的条目落 `原文依据` 并标 C 编号**，生成边界见 `test-knowledge-canon` §四。机验只校值域与「两类都必须有锚点」，不判定条目内容实际属于哪一类（语义判定归 QA 分路核查）；`summary.tp_methodology` / `summary.tc_methodology` 统计方法论补充条数，供观察覆盖率。

TP、TC 均**不设优先级列**，排序即优先级；排序按 `test-point-workflow` 方法链第 7 步（TC 跟着主 TP 成段）。**排序不进机验**：本脚本只校列名、锚点、值域、编号、数量守恒等逐行可判的事实；顺序须另行人工核对（同一业务功能连续、场景级 TP 在其所属功能段末尾、TC 按主 TP 成段且未被别的 TP 用例穿插）。

表头列名与脚本 `*_REQUIRED` 逐字一致（改列名须同步改脚本，双向核对）；值域、关联关系、数量守恒逐列符合本节及各 workflow skill 的取值规则。

## clarifications 表（7 列，列名与 `CLAR_REQUIRED` 逐字一致）

```text
编号 | 来源 | 问题 | 影响面 | 默认建议 | 答复 | 状态
```

| 字段 | 取值规则 |
|---|---|
| 编号 | `C-01` 起递增 |
| 来源 | QA 报告编号（第一道如 `qa-materials.md R1 · Q-M-R1-C1`，第二道缺口行如 `qa-materials.md R1 · Q-M-R1-D1`）或用户答复 |
| 影响面 | 写涉及条目的**当前**编号；条目重编号后**同步更新**（防指针漂移）；待澄清资料缺口类另写涉及的测试点与测试维度/小类 |
| 默认建议 | 具体可执行、可直接转成断言口径；不可执行的不算默认建议；待澄清资料缺口类固定为「静默生成：按四份原文知识链推导该测试点缺少的维度/小类/关注点的测试内容，仅写宽泛表述、不写具体值」 |
| 答复 | 可留空盛放原文答复；待澄清资料缺口类写 `静默生成` 或 `补充资料` + 用户补充的维度/小类资料描述与具体值 |
| 状态 | 仅 `待答复` / `默认生效` / `已答复` |

## verify_citation.py 调用形态

路径口径（本节的**路径口径**与「QA 抽验」节通用；换行写法以各节示例为准）：`SKILLS_ROOT` 为 `.opencode/skills/` 的**绝对路径**（部署时替换为实际值，禁止写相对路径）；`<根>`、`<会话>` 及 `--docs/--tp/--tc/--clar/--out` 一律展开为**工作空间内的绝对路径**，禁止相对路径。

仅 TP 时：

```bash
python3 SKILLS_ROOT/citation-verify/scripts/verify_citation.py \
  --docs <根>/project-docs --docs <会话>/user-input \
  --tp <会话>/output/tp/test-point-table.md --clar <会话>/state/clarifications.md \
  --out <会话>/state/citation-result.json
```

TP + TC 时：

```bash
python3 SKILLS_ROOT/citation-verify/scripts/verify_citation.py \
  --docs <根>/project-docs --docs <会话>/user-input \
  --tp <会话>/output/tp/test-point-table.md --tc <会话>/output/tc/test-case-table.md \
  --clar <会话>/state/clarifications.md --out <会话>/state/citation-result.json
```

校验项：

1. 每条锚点位置真实存在（行区间不越界 / docx 章节可寻位 / xlsx 单元格有值）
2. 摘抄与原文匹配（归一空白后子串比对，截断式摘抄按前缀匹配）且 ≤50 字
3. TC 的 `关联TP` 在 TP 清单存在
4. `澄清依据` 多值（` ;; ` 分隔，与锚点列同风格）逐段校验：`C-\d+`（可带 `(默认)`）在 clarifications.md 存在；整格 `-` 或空为无澄清
5. TP/TC 编号格式合法
6. TP 值域：`类型` ∈ {功能级, 场景级}；`测试维度` ∈《测试维度定义》§一十枚举；`所属小类` ∈ 所选维度下 §二合法小类集；`用例展开重点` 非空
7. TC 值域与一致性：`测试方法` ∈ 六枚举；`关联TP` 双段解析（编号段存在 + 名称段与 TP `测试点名称` 逐字一致）；`关联业务功能` 与主 TP 逐字一致
8. TC 对 TP 的覆盖缺口检查（无 TC 关联的 TP，仅警告）
9. **数量守恒检查**（`--tp` 与 `--tc` 同参时生效）：逐 TP 统计直属 TC 数 M，`M≥1` 且 `<2` 判 failures；`M=0` 不适用该判定，由覆盖缺口 warning 承载并须书面理由记 `state.md`
10. 表格完整性警告（仅警告，人工确认口径）：以 `|` 开头但未以 `|` 结尾的行会被解析跳过（单元格内真实换行，应使用 `<br>`）；文件解析出多个表格片段时首表之外的数据行不可见——两者均入 warnings 提示修复断行并整表重排
11. **依据类型检查**（TP/TC 通用）：`依据类型` 单值 ∈ {原文依据, 方法论补充}，空值或非法值判 failures；两类均要求 `出处锚点` 非空且逐条验真（校验项 1/2），方法论补充条目也不得凭空生成原文中不存在的字段/功能；`summary.tp_methodology` / `summary.tc_methodology` 给出方法论补充条数

输出 JSON：正常 payload 为 `{"ok", "summary", "failures": [{record, field, anchor, reason}], "warnings": [...]}`；**fatal 分支另输出含 `fatal_messages` 的 payload，退出码 2**。

退出码：0＝`failures` 为 0；1＝有失败项；2＝用法/致命错误（表头缺列、文件缺失等）。`warnings` 为需人工确认的提示项，含义见校验项 8/10。

`--out` 防护：输出文件名必须匹配 `citation-result*.json`，否则拒绝写入（防止脚本被挪作他用改写清单）。

## QA 抽验：inspect_anchor.py（只读，零写入能力）

**本约束仅适用于本节 `inspect_anchor.py`（QA 抽验，单行命令）**：命令须单行执行，不使用 `\` 换行。

```bash
python3 SKILLS_ROOT/citation-verify/scripts/inspect_anchor.py --docs <根>/project-docs --docs <会话>/user-input --anchor '<锚点>' [--anchor '<锚点2>' ...]
```

输出：每个锚点的解析结果、定位到的原文内容摘录、摘抄匹配判定。供逐条抽验 docx/xlsx 与可疑 md 锚点。

## 维护规则

锚点语法、表格解析、摘抄归一化的机器实现只在本目录 `scripts/` 三个文件（lib_citation.py 为核心实现，verify_citation.py / inspect_anchor.py 为入口）；其他 skill 或 agent 提示词不另写实现或复述判定逻辑。

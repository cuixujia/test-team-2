# 测试点工作流（生成：test-expert · 质检：test-qa-expert）

## 甲 · 生成流程（阶段 3）

### 输入四件套

scope.md 选中项、resources-index.md、clarifications.md、knowledge 方法链。先查索引定位原文片段再精读，不全文重读。

### 方法链（引用 skill `test-knowledge` 的 `references/` 原文，按序执行）

1. **维度选型**：读《测试维度定义》§三"维度选型指南"，按业务场景类型圈定 大类→测试维度→小类 组合
2. **维度关注点**：按圈定的小类读《通用测试规则》对应章节，拿到每个小类的详细关注点清单
3. **拆功能点**：按《测试点生成指南》§二：按业务模块从大到小拆到叶子功能点（CRUD 原子操作即叶子）；`同一功能含多个独立子功能`或`业务独立阶段分隔`才继续拆；层级 ≤5；跨模块全局场景才设"业务流程场景"节点
4. **命名测试点**：按指南 §三：功能级 = `验证+操作对象+基础功能`；场景级 = `验证+跨模块流程描述`。禁止：具体字段名/具体值/预期结果词（成功、不能、不可）出现
5. **颗粒度控制**：按指南 §四：一条 TP 必须能自然衍生 2~3 条正/反/边界用例；字段校验、落库、状态变更、消息触发归入"基础功能"TP，不单拆
6. **模板裁剪**：按指南 §五模板库匹配最接近的功能类型，按需增删，不机械全覆盖，不凑数、不臆造
7. **排序**：同一功能点下按 §六步骤6：正向 → 核心逻辑与状态 → 异常处理 → 边界与数据校验 → 其他

### 执行方式

按业务功能并行分片生成后再合并；合并时全局查重：功能级/场景级互斥（同一逻辑只在一个地方验证）。

### 自检（生成后必做，六项，指南 §六步骤5）

① 正向流程覆盖？② 反向/异常覆盖？③ 需求明确定义的独立业务规则有无遗漏？④ 有无臆造（需求未定义的内容→删除或"(默认)"标注）？⑤ 过度拆分（可合并）？⑥ 过度合并（需拆分）？

### 落盘模板（output/tp/list.md，6 列，列名与机验绑定不得改）

```markdown
# 测试点清单

| 编号 | 功能模块 | 测试点名称 | 类型 | 澄清依据 | 出处锚点 |
|---|---|---|---|---|---|
| TP-001 | 新增客户 | 验证新增界面展示正确性 | 功能级 | - | prd1.md:5 => "系统支持新增个人客户与对公客户" ;; prd1.md:12-14 => "客户名称长度不超过50个字符" |
| TP-002 | 新增客户 | 验证正常输入新增功能正确性 | 功能级 | C-01 | prd1.md:15 => "保存成功后状态置为待审核" |
| TP-003 | 客户管理 | 验证新增-审核-推送完整流程 | 场景级 | C-02(默认) | prd1.md:20-22 => "审核通过后触发推送" |
```

填写规则：
- 编号 `TP-001` 全局递增；类型：`功能级 / 场景级`
- 澄清依据：`-`（无依赖）、`C-01` 或 `C-01(默认)`（用户未答复，按默认建议生成）
- 出处锚点：每条 1~N 个，用 ` ;; ` 分隔；格式见 skill `citation-verify`（唯一口径）；单元格里禁止出现 `|` 字符
- 依赖默认建议或答复的条目，锚点必须指向支撑该判定的原文位置

### 送检门槛

跑 `verify_citation.py`，`failures` 必须为 0，否则修清单重跑（见 skill `citation-verify`）。

## 乙 · 质检维度（阶段 4，QA 全量检；大清单按功能分批连续检完）

| # | 维度 | 判定要点 | 分级参考 |
|---|---|---|---|
| 1 | 锚点真实性 | 每个功能模块抽验 ≥3 条：md 直读比对；docx/xlsx 用 inspect_anchor.py；锚点指向的原文必须真能支撑该 TP | 不实→阻塞 |
| 2 | 命名规范 | 指南 §三禁止清单：无"验证"开头风格漂移、无具体字段名/值、无预期结果词、无操作步骤入名 | 重大 |
| 3 | 颗粒度 | 1 TP 衍生能力 2~3；只对应单条用例→过细；一条含多个独立规则→过粗 | 重大 |
| 4 | 功能级/场景级互斥 | 场景级重复验证功能级已覆盖的单模块细节；同一逻辑两处出现 | 重大 |
| 5 | 全集覆盖 | 六查：正向/反常/独立规则遗漏/臆造/过细/过粗 | 缺失→阻塞（正向/反常/明定规则）或重大 |
| 6 | 范围一致性 | scope 选中功能的每个叶子功能点均有 TP；无范围外条目；场景级挂载位置正确 | 缺失→阻塞 |
| 7 | 排序 | 指南 §六步骤6 优先级顺序 | 一般 |
| 8 | 澄清/默认 | 澄清依据列编号在 clarifications.md 存在且语义一致；`(默认)` 条目重点核：默认建议是否被正确应用、是否引入新风险 | 误用→阻塞；风险→重大 |
| 9 | 臆造检测 | 依据锚点不可靠、或 TP 内容在原文与澄清记录中都找不到支撑 | 阻塞 |

## 报告格式（qa-tp.md，追加 `## R{N}` 小节，只追加不改写）

```markdown
## R{N}

**检查范围**：本次覆盖的功能模块与批次

### 问题清单
| 问题编号 | 分级 | 条目 | 问题描述 | 证据锚点 | 建议 |
|---|---|---|---|---|---|
| Q-TP-R1-01 | 重大 | TP-004 | 颗粒度过细…… | prd1.md:15 => "……" | 并入 TP-002 |

### 对照表复检（R2+）
| 问题编号 | 复检结果 | 核对说明 |
|---|---|---|

### 新增条目检查（R2+）
……

### 收敛判定
收敛 / 未收敛（剩余阻塞项：…）
```

R2+ 增量复检：只核 repair-log `## TP-R{n}` 小节条目 + 新增条目。收敛 = 无阻塞级问题。

## 纪律

QA 只检不修、每问题必有证据锚点；经理禁止自检替代本质检；模板列名是机器契约，增删列必须先改机验脚本再改模板（唯一口径在 skill `citation-verify`）。

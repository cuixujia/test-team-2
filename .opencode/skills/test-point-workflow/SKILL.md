# 测试点工作流（生成：测试专家 agent `test-expert` · 质检：质检专家 agent `qa-expert`）

## 甲 · 生成流程（阶段 3）

### 输入四件套

scope.md 选中项、resources-index.md、clarifications.md、knowledge 方法链。先查索引定位原文片段再精读，不全文重读。

### 方法链（引用 skill `test-knowledge` 的 `references/` 原文，按序执行）

1. **维度选型**：读《测试维度定义》§三"维度选型指南"，按业务场景类型圈定 大类→测试维度→小类 组合
2. **维度关注点**：按圈定的小类读《通用测试规则》对应章节，拿到每个小类的详细关注点清单
3. **拆功能点**：按《测试点生成指南》§二：按业务模块从大到小拆到叶子功能点（CRUD 原子操作即叶子）；`同一功能含多个独立子功能`或`业务独立阶段分隔`才继续拆；层级 ≤5；跨模块全局场景才设"业务流程场景"节点。拆分细节按下方【切分判别细则】执行
4. **命名测试点**：按指南 §三：功能级 = `验证+操作对象+基础功能`；场景级 = `验证+跨模块流程描述`。禁止：具体字段名/具体值/预期结果词（成功、不能、不可）出现。命名口径按下方【命名判据与词面筛检】执行
5. **颗粒度控制**：按指南 §四 + 裁决一：一条 TP 必须能自然衍生至少 2 条正/反/边界用例（上限以维度数封顶；只对应用例→过细需向上合并，处置见裁决五）；字段校验、落库、状态变更、消息触发归入"基础功能"TP，不单拆
6. **模板裁剪**：按指南 §五模板库匹配最接近的功能类型，按需增删，不机械全覆盖，不凑数、不臆造
7. **排序**：同一功能点下按 §六步骤6：正向 → 核心逻辑与状态 → 异常处理 → 边界与数据校验 → 其他（同一功能点归属诠释见裁决六 B2）

### 切分判别细则（对《测试点生成指南》§4.1「独立规则」的 PRD 锚定）

- **合并规则**：PRD 将多个条件**并列列在同一业务能力下**，且没有为它们规定不同的流程、规则、权限或结果 → 合成一条。即使某项可能单独出错，也不因此拆分；该项由 TC 单独覆盖。
- **拆分规则**（仅以下情况拆分）：
  1. 条件属于**不同业务能力或不同业务目标**
  2. PRD **明文规定**了不同的流程、规则、权限或结果
  3. **主项与副项**承担不同作用，且 PRD 对两者规定了不同的操作或验收要求
- 字段、数据、角色、控件不同，或其中一项可单独失败——**本身都不是拆分理由**。
- **描述不清**：PRD 没说明并列条件是否存在不同规则 → 先按同一目标合并成一条，该模糊点交澄清，**不得自行补造规则**。

**质检两句话**：

- **该拆**：两种结果出自 PRD 明文规定的不同流程/规则/权限/结果，或分属不同业务目标 → 拆成两条。
- **该合**：同一业务能力下的并列条件、或同一规则下的不同数据/对象/角色 → 合成一条（由 TC 覆盖各维度）。

**三违规**：

1. **太大**：把 PRD 写明不同规则的多条业务塞进一条（如「验证转账功能正确」）
2. **太小**：同一套处理的不同数据拆成多条——若 PRD 对 0 和负数写的是同一套「拒绝并提示」，具体数据是用例的事
3. **耦合**：验证明细维度的存在性/生效性与其所属能力验证重复 → 只保留能力级验证，细则由 TC 覆盖

### 命名判据与词面筛检（生成端出稿前逐条自查、质检端逐条过一遍）

格式本身以《测试点生成指南》§三为权威。团队约定与词法：

- 对象**直接抄 PRD 的叫法**，不自创同义词——名称是未来用例库检索键。
- 短语级（≤30 字），保持同清单内命名风格一致。
- **验证意图词面筛检**（对知识④§1.3 禁止项④与 §3.1 语言要求"不出现具体字段名、具体值、处理逻辑和预期结果"的可执行形态）：
  1. **结果词**：不出现「成功 / 不能 / 不可 / 进入…状态 / 自动生成」类词汇（名称承载"验证什么"的方向，不承载执行能否达成）；
  2. **处理逻辑**：不出现「返回…信息 / 保存到…」类执行过程描述；
  3. **具体值**：不出现数字字面量与其他具体值（如"25 字符""2-50 个字符"）；
  4. **并列双结果谓词**：意图里以「并 / 且」串联两个结果必须自查：两结果出自同一套自动留存处理→可合；PRD 规定了不同规则→拆。
- **验证词去重**：名内「验证」仅出现一次；「验证XX功能验证」式词面重复判错（如「验证高级搜索功能验证」❌）。
- **过粗校正**（「验证XX功能」式，如「验证新增功能」）：仅当该 TP 的直属 TC 承载**两类及以上判定维度**（字段校验、落库、默认值、消息提醒等各自独立计）时判合规，否则按指南 §4.1「一条测试点涵盖多个独立规则→拆分」或过粗表现处置；不入下限词法硬规则（避免错杀）。
- **例外**：PRD 原词照抄场景（对象名/状态名）不因词面命中而判错，按主从裁决与直引证据认定。

**判错示例口袋清单**：

| 示例 | 判定 |
|---|---|
| 验证转账功能正确 | ❌ 几条不同业务规则塞一条，没法判（=指南 §4.1 过粗） |
| 验证输入 0 元和负数均被拒绝 | ❌ PRD 写的是同一套处理——具体数据是用例的事 |
| 验证系统能转账 | ❌ 功能描述，不是验证（=指南 §1.1 功能点≠测试点） |
| 验证需求创建成功后进入待沟通状态 | ❌ 含结果词「成功」+ 状态变更执行结果（=词面筛检 1） |
| 验证修改标题必填校验与 25 字符长度上限 | ❌ 含具体值 + 字段边界独立成测试点（=词面筛检 3） |
| 验证修改标题自动生成默认标题 | ❌ 含处理逻辑「自动生成」（=词面筛检 2） |
| 验证新增标题并返回需求 ID 与会话信息 | ❌ 并列双结果谓词「并」串联两个执行结果，需先判合并/拆分（=词面筛检 4） |

### 执行方式

按业务功能并行分片生成后再合并；合并时全局查重：功能级/场景级互斥（同一逻辑只在一个地方验证）。

### 自检（生成后必做，六项，指南 §六步骤5）

① 正向流程覆盖？② 反向/异常覆盖？③ 需求明确定义的独立业务规则有无遗漏？④ 有无臆造（需求未定义的内容→删除或"(默认)"标注）？⑤ 过度拆分（可合并）？⑥ 过度合并（需拆分）？

| 字段 | 取值规则 |
|---|---|
| 编号 | `TP-001` 三位数字起步；重排后**必须重编号**（连续无跳号） |
| 关联业务功能 | 关口 1 用户选定的业务功能：F 编号 + PRD 原文名称（如 `F01 · 需求创建`）；禁自创模块词；场景级条目带"（局部场景）"标注 |

| 澄清依据 | 无：`-`；有：`C-编号` 或 `C-编号(默认)`；多值 ` ;; ` 分隔；编号必须存在于 clarifications.md（clarifications 表见 skill `citation-verify`） |
| 出处锚点 | 按 skill `citation-verify` 锚点口径：至少 1 条，一般 1~3 条 |

### 送检门槛

`failures` = 0 才送检（机验命令见 skill `citation-verify`"生成端送检前"节）；重试与异常处置（exit 2 / 三振上限）按测试专家机验规则。`warnings`（覆盖缺口）人工确认并记 state.md。

## 乙 · 质检维度（阶段 4，QA 全量检；大清单按功能分批连续检完）

| # | 维度 | 判定要点 | 分级参考 |
|---|---|---|---|
| 1 | 锚点真实性 | 每个功能模块抽验 ≥3 条：md 直读比对；docx/xlsx 用 inspect_anchor.py；锚点指向的原文必须真能支撑该 TP | 不实→阻塞 |
| 2 | 命名规范 | 按甲节【命名判据与词面筛检】全项核查（含判错示例口袋清单）：风格漂移、结果词、处理逻辑、具体值、并列双结果谓词、验证词重复均判错 | 重大 |
| 3 | 颗粒度 | 1 TP 直属 TC ≥2（不足且维度 ≥2 判展开不足，裁决一/五）；只对应单条用例→过细；一条含多个独立规则→过粗 | 重大 |
| 4 | 功能级/场景级互斥 | 场景级重复验证功能级已覆盖的单模块细节；同一逻辑两处出现 | 重大 |
| 5 | 全集覆盖 | 六查：正向/反常/独立规则遗漏/臆造/过细/过粗 | 缺失→阻塞（正向/反常/明定规则）或重大 |
| 6 | 范围一致性 | scope 选中功能的每个叶子功能点均有 TP；无范围外条目；场景级挂载位置正确 | 缺失→阻塞 |
| 7 | 排序 | 指南 §六步骤6 优先级顺序；簇内排列按裁决六 B2 | 一般 |
| 8 | 澄清/默认 | 澄清依据列编号在 clarifications.md 存在且语义一致；`(默认)` 条目重点核：默认建议是否被正确应用、是否引入新风险 | 误用→阻塞；风险→重大 |
| 9 | 臆造检测 | 依据锚点不可靠、或 TP 内容在原文与澄清记录中都找不到支撑 | 阻塞 |

## 报告格式（qa-tp.md，追加 `## R{N}` 小节，只追加不改写）

```markdown
## R{N}

**检查范围**：本次覆盖的功能模块与批次

### 问题清单
| 问题编号 | 分级 | 条目 | 问题描述 | 证据锚点 | 建议 |
|---|---|---|---|---|---|
| Q-TP-R1-01 | 重大 | TP-004 | 颗粒度过细…… | prd1.md:15 => "……" | 并入 TP-002 |

### 对照表复检（R2+）
| 问题编号 | 复检结果 | 核对说明 |
|---|---|---|

### 新增条目检查（R2+）
……

### 收敛判定
收敛 / 未收敛（剩余阻塞项：…）
```

R2+ 增量复检：只核 repair-log `## TP-R{n}` 小节条目 + 新增条目。收敛 = 无阻塞级问题。

## 纪律

QA 只检不修、每问题必有证据锚点；测试专家禁止自检替代质检专家检；模板列名是机器契约，增删列必须先改 skill `citation-verify` 机验脚本再改模板。格式问题（锚点格式/表头列名/摘抄长度/横线）由测试专家机验前置拦下，**不进质检范围**。

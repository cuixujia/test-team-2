# 测试点判据（TP）

## 生成判据

### 方法链（引用 `test-knowledge-canon` 的 `references/` 原文，按序）

1. **维度选型**：读《测试维度定义》§三"维度选型指南"，按业务场景类型圈定 大类→测试维度→小类 组合；本轮圈定的**测试维度/所属小类**即在落盘时随条目填入对应列（见落盘模板取值规则），不另设基线产物
2. **维度关注点**：按圈定的小类读《通用测试规则》对应章节，拿到每个小类的详细关注点清单；关注点经模板裁剪后写入条目 `用例展开重点` 列
3. **拆功能点**：按《测试点生成指南》§二：按业务模块从大到小拆到叶子功能点（CRUD 原子操作即叶子）；`同一功能含多个独立子功能`或`业务独立阶段分隔`才继续拆；层级 ≤5；跨模块全局场景才设"业务流程场景"节点。拆分细节按【切分判别细则】执行
4. **命名测试点**：按指南 §三：功能级 = `验证+操作对象+基础功能`；场景级 = `验证+跨模块流程描述`。禁止：具体字段名/具体值/预期结果词（成功、不能、不可）出现。命名口径按【命名判据与词面筛检】执行
5. **颗粒度控制**：按指南 §四：一条 TP 应能自然衍生 2~3 条正/反/边界用例；只对应 1 条用例→过细需向上合并；字段校验、落库、状态变更、消息触发归入"基础功能"TP，不单拆。`用例展开重点` 的项数 N 按 PRD 客观计数枚举（字段校验类=字段数×约束类型数、状态流转类=合法边数+非法边、查询筛选类=查询项数、权限类=角色×操作、容错类=外部依赖数、场景类=基本流+备选流），**是展开数量目标——TC 生成按 N 逐项落、M≥N（口径见 `test-case-workflow`「展开数量守恒」），不是机验下限**；机验下限见 `citation-verify`「清单表机器契约」
6. **模板裁剪与两路生成**：按指南 §五模板库匹配最接近的功能类型，按需增删，不机械全覆盖、不凑数。资料已描述该维度/小类内容的按锚点裁剪，落 `原文依据`；资料未描述、由模型按 `test-knowledge-canon` §四 依四份原文知识链或测试经验判断自由发挥补出的测试内容，一律落 `方法论补充`（对象须有原文锚点、静默生成时不写具体值）。两类都不得新增原文没有的对象、不得补造业务规则。
7. **排序规则**（段间与簇内一律按本步）：
   - `关联业务功能` 相同的 TP 必须排在一起，中间不插别的功能；段的先后按 scope 选中项顺序（F01、F02……）。不许出现 F01 → F02 → 又回到 F01。
   - 每一段内部：先写该功能的全部功能级 TP，同层内按 **正向 → 核心逻辑与状态 → 异常处理 → 边界与数据校验 → 其他** 人工核对，再把该功能的场景级 TP 放在这一段最后。
   - 场景级 TP 属于哪个业务功能（看流程起点 / 主要承载功能），就放进那一段，不要集中放到整张清单最后。例：F01 的"验证需求创建-受理完整流程"紧跟 F01 段最后一条功能级 TP，下一条才是 F02 的 TP。
   - 归属拿不准时，查主件的功能归属说明或需求→TP 覆盖表。
   - 排序须人工逐行核对；口径见 `citation-verify`「清单表机器契约」。

### 切分判别细则（对《测试点生成指南》§4.1「独立规则」的 PRD 锚定）

- **合并规则**：PRD 将多个条件**并列列在同一业务能力下**，且没有为它们规定不同的流程、规则、权限或结果 → 合成一条。即使某项可能单独出错，也不因此拆分；该项由 TC 单独覆盖。
- **拆分规则**（仅以下情况拆分）：
  1. 条件属于**不同业务能力或不同业务目标**
  2. PRD **明文规定**了不同的流程、规则、权限或结果
  3. **主项与副项**承担不同作用，且 PRD 对两者规定了不同的操作或验收要求
- 字段、数据、角色、控件不同，或其中一项可单独失败——**本身都不是拆分理由**。
- **描述不清**：PRD 没说明并列条件是否存在不同规则 → 先按同一目标合并成一条，该模糊点交澄清，**不得自行补造规则**。

**质检两句话**：

- **该拆**：两种结果出自 PRD 明文规定的不同流程/规则/权限/结果，或分属不同业务目标 → 拆成两条。
- **该合**：同一业务能力下的并列条件、或同一规则下的不同数据/对象/角色 → 合成一条（由 TC 覆盖各维度）。

**三违规**：

1. **太大**：把 PRD 写明不同规则的多条业务塞进一条（如「验证转账功能正确」）
2. **太小**：同一套处理的不同数据拆成多条——若 PRD 对 0 和负数写的是同一套「拒绝并提示」，具体数据是用例的事
3. **耦合**：验证明细维度的存在性/生效性与其所属能力验证重复 → 只保留能力级验证，细则由 TC 覆盖

### 查询/筛选类专项（落"合而不丢"口径）

- **合并**：查询项/筛选项（字段、条件）在 PRD 中**并列列出且未规定不同流程、规则、权限或结果** → 合成一条 TP；该 TP 的 `用例展开重点` **必须逐查询项点名**（如 `按名称筛选 ;; 按编号筛选 ;; 按状态筛选`），项数 N=查询项数，作为展开充分性建议——逐项覆盖的要求由 TP 承载、实现在 TC 层展开，合而不丢
- **拆分**：PRD 对不同查询项**明文规定不同结果/规则/权限** → 按上方拆分规则第 2 条拆 TP
- **不硬塞**：某查询项确实分属不同业务能力时沿用合并规则的禁令，不为了省条数塞一条

**质检两句话**：该合——同套处理的查询项合成一条，且 `用例展开重点` 点名逐项用例；该拆——PRD 明文规定不同规则/结果，仍把多个查询项塞一条。

**三违规（查询版）**：把 PRD 写明不同规则的多条查询塞一条；把同套处理的查询项拆成多条；查询项在 `用例展开重点` 中无逐项点名加载（丢项风险）。

### 命名判据与词面筛检

格式本身以《测试点生成指南》§三为权威。团队约定与词法：

- 对象**直接抄 PRD 的叫法**，不自创同义词——名称是未来用例库检索键。
- 短语级（≤30 字），保持同清单内命名风格一致。
- **验证意图词面筛检**（对知识④§1.3 禁止项④与 §3.1 语言要求"不出现具体字段名、具体值、处理逻辑和预期结果"的可执行形态）：
  1. **结果词**：不出现「成功 / 不能 / 不可 / 进入…状态 / 自动生成」类词汇（名称承载"验证什么"的方向，不承载执行能否达成）；
  2. **处理逻辑**：不出现「返回…信息 / 保存到…」类执行过程描述；
  3. **具体值**：不出现数字字面量与其他具体值（如"25 字符""2-50 个字符"）；
  4. **并列双结果谓词**：意图里以「并 / 且」串联两个结果必须自查：两结果出自同一套自动留存处理→可合；PRD 规定了不同规则→拆。
- **验证词去重**：名内「验证」仅出现一次；「验证XX功能验证」式词面重复判错（如「验证高级搜索功能验证」❌）。
- **过粗校正**（「验证XX功能」式，如「验证新增功能」）：仅当该 TP 的直属 TC 承载**两类及以上判定维度**（字段校验、落库、默认值、消息提醒等各自独立计）时判合规，否则按指南 §4.1「一条测试点涵盖多个独立规则→拆分」或过粗表现处置；不入下限词法硬规则（避免错杀）。
- **例外**：PRD 原词照抄场景（对象名/状态名）不因词面命中而判错，按主从判定与直引证据认定。

**判错示例口袋清单**：

| 示例 | 判定 |
|---|---|
| 验证转账功能正确 | ❌ 几条不同业务规则塞一条，没法判（=指南 §4.1 过粗） |
| 验证输入 0 元和负数均被拒绝 | ❌ PRD 写的是同一套处理——具体数据是用例的事 |
| 验证系统能转账 | ❌ 功能描述，不是验证（=指南 §1.1 功能点≠测试点） |
| 验证需求创建成功后进入待沟通状态 | ❌ 含结果词「成功」+ 状态变更执行结果（=词面筛检 1） |
| 验证修改标题必填校验与 25 字符长度上限 | ❌ 含具体值 + 字段边界独立成测试点（=词面筛检 3） |
| 验证修改标题自动生成默认标题 | ❌ 含处理逻辑「自动生成」（=词面筛检 2） |
| 验证新增标题并返回需求 ID 与会话信息 | ❌ 并列双结果谓词「并」串联两个执行结果，需先判合并/拆分（=词面筛检 4） |

### 全集自检六项（指南 §六步骤 5）

① 正向流程覆盖？② 反向/异常覆盖？③ 需求明确定义的独立业务规则有无遗漏？④ 有无臆造（按 `依据类型` 分路：`原文依据` 需求未定义的内容→删除或"(默认)"标注；`方法论补充` 核对象锚点、补充边界与静默生成不得写具体值，见 `test-knowledge-canon` §四）？⑤ 过度拆分（可合并）？⑥ 过度合并（需拆分）？

| 关联业务功能 | 范围确认选定的业务功能：**第一个空格分隔** F 编号与 PRD 原文名称（如 `F01 需求新增`）；禁自创模块词 |
| 测试点名称 | 依方法链第 4 步【命名判据与词面筛检】 |
| 类型 | 仅 `功能级` / `场景级`；按**验证范围**分型（指南 §1.2）：单功能点内=功能级，跨功能点链路=场景级；性能/安全等非功能维度测试点适用同一标尺，不改变分型 |
| 测试维度 | 单值；= 维度选型（§三选型指南）圈定组合中该 TP 归属的**测试维度层**：`基础功能`/`业务流程`/`界面与体验（UI/UX）`/`数据校验`/`权限控制`/`接口 API 测试`/`性能`/`安全`/`兼容性与多端`/`可靠性与稳定性`；值域机验见 `citation-verify` |

| 用例展开重点 | 短语级，建议 2~3 项以上，` ;; ` 分隔；**机验只校非空**，项数 N 是展开充分性的人工建议、不是 TC 数量下限（下限口径见 `citation-verify`「清单表机器契约」）。每一项须是**一个可独立判定的展开分支**，按 PRD 客观计数枚举：字段校验逐字段×约束、状态流转逐条合法边+非法边、查询筛选逐查询项、权限逐角色×操作、容错逐外部依赖、场景基本流+各备选流。**字段校验的约束 = 原文已给约束 + 按 ②§二 1.2「字段校验」关注点 + ③§1.2 六大固定场景发散的约束（长度/格式/枚举/精度/特殊字符/空格/脚本等），后者同样计入 N 的客观枚举**，以提高覆盖率。**禁止把通则写成项**——"每项至少 1 条用例""覆盖正向反向""基本流正向贯通"类元描述不计入 N。来源=指南 §五模板库右列 + 《通用测试规则》对应维度关注点裁剪；供 TC 展开直接消费 |
| 依据类型 | 仅 `原文依据` / `方法论补充`（值域机验见 `citation-verify`）。`原文依据` = 测试内容由 `出处锚点` 或澄清答复直接推导；`方法论补充` = 资料未描述、由模型自由发挥补出的测试内容（发散依据为四份原文知识链或测试经验判断的应测点），定义与五条边界见 `test-knowledge-canon` §四。**静默生成的缺口与任何自由发挥条目一律 `方法论补充`；补充资料后按答复写出的条目落 `原文依据`**。静默生成条目 `澄清依据` 写 `-`；补充资料的条目在 `澄清依据` 标对应 C 编号。两类都须有 `出处锚点`（对象锚点），原文没有的字段/功能不得出现 |
| 澄清依据 | 无：`-`；有：`C-编号` 或 `C-编号(默认)`；多值 ` ;; ` 分隔；编号必须存在于 clarifications.md（clarifications 表见 `citation-verify`） |
| 出处锚点 | 按 `citation-verify` 锚点口径：至少 1 条，一般 1~3 条；两类依据类型都必须有，锚点口径第 7 条区分内容锚点与对象锚点 |

## 质检判据（九维）

| # | 维度 | 判定要点 | 分级参考 |
|---|---|---|---|
| 1 | 锚点真实性 | 每个功能模块抽验 ≥3 条：md 直读比对；docx/xlsx 用 inspect_anchor.py。`原文依据` 条目的锚点须真能支撑该 TP 的判定性内容；`方法论补充` 条目的锚点只需证明验证对象在原文存在（对象锚点），不要求支撑发散出的测试内容；**原文没有的字段/功能却生成了测试内容 → 阻塞** | 不实→阻塞；虚构对象→阻塞 |
| 2 | 命名规范 | 按【命名判据与词面筛检】全项核查（含判错示例口袋清单）：风格漂移、结果词、处理逻辑、具体值、并列双结果谓词、验证词重复均判错 | 重大 |
| 3 | 颗粒度 | 两条路径分阶段执行——**TC 未生成时定性筛**：看到 TP 应能自行展开为 2~3 条正/反/边界用例，展开不了即问题；**TC 已生成时计数筛**：逐 TP 核对直属 TC 数 `M≥2`（`M=0` 由覆盖缺口 warning 承载并须书面理由记 `state.md`），**`M≥1` 且 `<2` 即判"展开不足"，判阻塞**；`用例展开重点` 项数 N 按方法链第 5 步算法复核（字段×约束/状态边数/查询项数/角色×操作/外部依赖数），**双向判定**——N 明显少于 PRD 客观分支 → 问题记在 TP（过粗），要求拆 TP 而非只补 TC；TC 数 `M<N` → 问题记在 TC 展开（不足），逐项补 TC 而非凑数；**均一化红线**：过半 TP 的 M 完全相同且与算法建议不符→判整批凑数；只对应单条用例→过细；一条含多个独立规则→过粗；**查询/筛选类另项**：查询项已在 `用例展开重点` 逐项点名，而某查询项仅有 1 条 TC 或完全无 TC 且无书面豁免 → 判"展开不足" | 阻塞（M<2、M<N、均一化）；其余重大 |
| 4 | 功能级/场景级互斥 | 场景级重复验证功能级已覆盖的单模块细节；同一逻辑两处出现 | 重大 |
| 5 | 全集覆盖 | 六查：正向/反常/独立规则遗漏/臆造（分路见维度 9）/过细/过粗；另按方法链第 1 步维度选型圈定的**小类**逐一对表 TP `所属小类` 列——每个圈定小类至少 1 条 TP 对应，缺失判**阻塞**（选型空转=圈了不测）；**覆盖率复查**：按 `state/clarifications.md` 的待澄清资料缺口处置决策与 `qa-materials.md` R1 待澄清资料缺口表，清单列出的测试维度/小类/关注点是否有对应 TP，缺失判重大；**选型圈定组合不落盘**，以《测试维度定义》§三选型指南按需求形态重新推导为准，与生成端不一致时以指南条款为判定依据，不得凭各自判断互相否决 | 缺失→阻塞（正向/反常/明定规则/小类全覆盖）或重大；方法论维度漏补→重大 |
| 6 | 范围一致性 | scope 选中功能的每个叶子功能点均有 TP；无范围外条目；场景级挂载位置正确 | 缺失→阻塞 |
| 7 | 排序 | 三看：① 同一业务功能的 TP 有没有排在一起（不许 F01→F02→又回 F01）；② 段内是不是功能级在前、场景级收尾，段内顺序按方法链第 7 步人工核对；③ 场景级 TP 有没有放在它所属功能那一段里，而不是整张清单最末 | 一般（段内乱序）；功能段被打断、场景级放错段 → 重大 |
| 8 | 澄清/默认 | 澄清依据列编号在 clarifications.md 存在且语义一致；`(默认)` 条目重点核：默认建议是否被正确应用、是否引入新风险 | 误用→阻塞；风险→重大 |
| 9 | 臆造检测（按 `依据类型` 分路） | `原文依据`：锚点不可靠、或 TP 内容在原文与澄清记录中找不到支撑 → 阻塞；`方法论补充`：只判四项——对象锚点不真实或验证对象不在原文、补充的测试维度/所属小类/关注点不属于知识链或测试经验判断的应测范围、或未按该关注点发散、静默生成却写死具体数值/枚举值/文案、借补充之名补造业务规则或新增字段/功能 → 阻塞。合规的方法论补充**不得**仅因"原文没描述该维度/小类"判臆造，边界见 `test-knowledge-canon` §四 | 阻塞 |

# 测试点生成指南

> 本文档定义测试点的概念、命名规范、颗粒度、模板库和生成工作流程。
> 与《测试维度定义》《通用测试规则》配合使用；若用户提供了业务规则，则参考用户的规则，形成完整的"骨架→通用规则→测试方法→测试点"测试点生成办法。

---

## 一、核心概念定义

### 1.1 功能点 vs 测试点

| 概念      | 描述"什么"         | 说明                                                              |
| ------- | -------------- | --------------------------------------------------------------- |
| **功能点** | 描述"**系统能做什么**" | 按业务模块和系统操作能力从大到小划分；叶子功能点是系统中可独立存在的最小操作单元（如"账号校验"、"入账处理"、"新增功能"） |
| **测试点** | 描述"**验证什么**"   | 按验证目标分为功能级和场景级两类；是概念层面的验证目标，测试人员看到后应能自行展开为多条正/反/边界用例            |

**关键原则**：
- 不要按"功能性/场景性"对功能点分类，功能点只按系统能力划分
- 业务流程场景作为独立的功能模块存在，用于承载跨模块的全局场景级测试点

### 1.2 功能级测试点 vs 场景级测试点

| 类型         | 验证范围              | 聚焦问题  | 挂载位置                                                    |
| ---------- | ----------------- | ----- | ------------------------------------------------------- |
| **功能级测试点** | 单功能点内的逻辑、规则、边界、异常 | "对不对" | 挂在对应的叶子功能点下                                             |
| **场景级测试点** | 跨功能点的完整业务链路       | "通不通" | 局部场景（涉及2个模块）挂在核心模块或发起方模块下；全局场景（涉及3+个模块）挂在独立的"业务流程场景"模块下 |

**两者互斥，不要重复**：
- 场景级测试点只验证链路通畅，不重复验证功能级已覆盖的单模块细节
- 如果某个逻辑已在功能级测试点中覆盖，场景级测试点中不得再次出现

### 1.3 测试点 vs 测试用例的边界

| 层级      | 回答的问题        | 包含内容            | 粒度判断标准                                                |
| ------- | ------------ | --------------- | ----------------------------------------------------- |
| **测试点** | "验证哪个维度的正确性" | 概念层面的验证目标       | 一个测试点应能自然衍生出至少 2~3 条正/反/边界用例；如果只对应单条用例，说明太细，需向上合并     |
| **用例**  | "怎么测"        | 具体输入值、操作步骤、预期结果 | 字段级校验、落库验证、状态变更、消息触发等属于同一操作的执行结果，统一归入"基础功能"测试点，在用例层展开 |

**禁止行为**：
- ✗ 将单个字段的校验作为独立测试点（如"验证XX字段落库"、"验证XX字段非空"）
- ✗ 将具体操作步骤写入测试点名称（如"点击保存后验证状态变更"）
- ✗ 将多条同维度校验拆散为多个测试点（如回写的处理状态、应对措施、实际影响应合并为一个测试点）
- ✗ 在测试点名称中出现预期结果词汇（如"成功"、"不改变"、"不可"等）

## 二、功能点拆分规则

### 2.1 拆分原则

| 原则 | 说明 |
|------|------|
| 语言精炼 | 以一个词或短语表示，避免句子或段落 |
| 体现系统能力 | 描述系统操作能力，而非用户行为或测试行为 |
| 独立划分 | 根据业务模块、功能类型等从大到小划分，确保功能点独立、清晰 |
| 排除测试行为 | 不包含测试、验证等行为，也不包含用户输入的具体内容（如任务名称） |

### 2.2 叶子功能点的判定标准

CRUD类原子操作（新增/编辑/删除/复制等单一角色的连续操作）**本身就是叶子功能点**，下面直接挂载测试点。

数据落库、消息触发、状态变更等属于原子操作的执行结果，**不作为独立的功能点进行拆分**。只有当出现以下两种情况之一时才拆分：

| 条件 | 说明 | 示例 |
|------|------|------|
| **同一功能下包含多个独立的子功能** | 同一操作名下包含多个参数体系或业务逻辑完全不同的独立功能 | "新增客户"下含"新增个人"和"新增对公"，二者字段、校验、规则各不相同 |
| **同一功能下业务独立阶段分隔** | 同一功能的业务流程包含多个独立的业务阶段节点 | 多角色审批：提交→负责人审核→管理人复核→主管确认 |

### 2.3 业务流程场景的判定条件

测试重点存在跨多功能模块的全局性场景时，才需要有对应的"业务流程场景"功能节点；不需要的则不新增该节点。

- 示例："转账完整流程"、"入账预警流程"

### 2.4 拆分层级限制

- 功能点层级不超过 5 层（不包括根节点与测试点）
- 功能点的子节点只能全部为功能点或者全部为测试点；测试点为最后一个层级，不能再有子节点

## 三、测试点命名规范

### 3.1 功能级测试点命名

**格式**：`验证` + `操作对象` + `基础功能`

| 要素 | 说明 |
|------|------|
| 操作对象 | 被验证的功能模块或数据实体（如"新增功能"、"管理人审核"、"导出文件"） |
| 语言要求 | 精简，一个短语即可；不出现具体字段名、具体值、处理逻辑和预期结果 |

**示例**：

| ✓ 正确 | ✗ 错误 | 原因 |
|--------|--------|------|
| 验证风险新增基础功能 | 验证风险内容长度边界 | 后者太细，字段边界验证属于用例级 |
| 验证风险可删除的状态范围 | 验证风险内容不能为空 | 后者出现预期结果词汇"不能" |
| 验证各字段控件类型、必填及取值逻辑正确性 | 验证姓名长度为2-50个字符 | 后者是具体用例，不是测试点 |

### 3.2 场景级测试点命名

**格式**：`验证` + `跨模块流程描述`

可用"-"串联关键节点，体现链路而非细节。

**示例**：

| ✓ 正确 | ✗ 错误 | 原因 |
|--------|--------|------|
| 验证新增-提醒-审核通过-推送雪狼完整流程 | 验证审核通过后状态变为已审核 | 后者是功能级，不是场景级 |
| 验证审核拒绝-关闭-不推送流程 | 验证报文校验通过触发入账流程挂在入账处理下 | 后者是局部场景，命名应体现场景流程概念 |

### 3.3 禁止行为清单

| 禁止项    | 说明                                   |
| ------ | ------------------------------------ |
| 不机械全覆盖 | 不要机械地为每个功能点都生成功能级+场景级测试点             |
| 不凑数    | 不要生成无意义的测试点（如"验证XX功能存在"、"验证XX页面能打开"） |
| 不重复    | 场景级测试点不要重复覆盖功能级已验证的单一节点              |
| 不臆造    | 每个测试点必须源自需求文档，不臆造不存在的功能              |

## 四、测试点颗粒度控制

### 4.1 粒度判断标准

| 标准 | 说明 |
|------|------|
| 衍生能力 | 一个测试点应能自然衍生出至少 2~3 条正/反/边界用例 |
| 合并判断 | 字段级校验、落库验证、状态变更、消息触发等属于同一操作的执行结果，统一归入"基础功能"测试点 |
| 过细表现 | 只对应单条用例 → 太细，需向上合并 |
| 过粗表现 | 一条测试点涵盖多个独立规则 → 需要拆分 |

### 4.2 典型颗粒度示例

以"新增功能"为例，以下测试点构成概念上的全集：

```
验证新增界面展示正确性              （UI：页面布局、元素可见性）
验证各字段控件类型、必填及取值逻辑正确性  （字段校验：控件类型、必填项、字典取值等归为一个维度）
验证字段默认值正确                  （默认值：自动填充、默认选项等）
验证正常输入新增功能正确性           （正向：主流程走通、数据落库、状态变更归为一个维度）
验证新增功能特殊操作场景             （特殊场景：选填项为空、特殊字符、超长输入等）
验证新增入口                        （前置条件：谁能看到入口、在什么状态下可操作）
验证新增后消息提醒                  （关联行为：提醒触发、接收人、内容定位归为一个维度）
验证新增功能权限控制                （安全：操作权限+越权拦截）
验证并发提交                        （约束：防重提交、并发冲突处理）
```

注意：以上每条都是"验证维度"，不是"验证项"。测试人员看到"验证各字段控件类型、必填及取值逻辑正确性"后，应能自行展开为针对每个字段的多条用例。

## 五、典型测试点模板库

> 以下模板按功能类型分类，左列为测试点名称，右列为用例展开时应关注的重点。
> 参考这些模板的颗粒度和覆盖范围，根据实际需求裁剪，不要机械套用。

### 5.1 CRUD类（新增/编辑/删除/复制）

**新增类：**

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证新增界面展示正确性 | UI：页面布局、元素可见性 |
| 验证各字段控件类型、必填及取值逻辑正确性 | 字段校验：控件类型、必填项、字典取值等归为一个维度 |
| 验证字段默认值正确 | 默认值：自动填充、默认选项等 |
| 验证正常输入新增功能正确性 | 正向：主流程走通、数据落库、状态变更归为一个维度 |
| 验证新增功能特殊操作场景 | 特殊场景：选填项为空、特殊字符、超长输入等 |
| 验证新增入口 | 前置条件：谁能看到入口、在什么状态下可操作 |
| 验证新增后消息提醒 | 关联行为：提醒触发、接收人、内容定位归为一个维度 |
| 验证新增功能权限控制 | 安全：操作权限+越权拦截 |
| 验证并发提交 | 约束：防重提交、并发冲突处理 |

**修改类：**

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证修改界面展示及内容回显正确性 | UI+回显：页面布局、原有数据回显 |
| 验证修改界面各字段属性校验规则同新增功能 | 字段校验：复用新增的校验规则体系 |
| 验证正常输入修改功能正确性 | 正向：修改生效、数据更新、状态流转 |
| 验证不可编辑字段不可被修改 | 约束：只读字段保护 |
| 验证修改功能特殊操作场景 | 特殊场景：部分字段修改、关联数据影响等 |
| 验证修改功能权限控制 | 安全：操作权限+越权拦截 |
| 验证修改入口 | 前置条件：谁能看到入口、在什么状态下可编辑 |
| 验证并发提交 | 约束：并发修改冲突处理 |

**删除类：**

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证正常删除功能正确性 | 正向：删除生效、数据清除、关联数据清理 |
| 验证不可删除的状态/条件拦截 | 约束：已关联、已审批等状态下禁止删除 |
| 验证删除后关联数据清理 | 数据一致性：级联删除或置空策略正确 |
| 验证删除功能权限控制 | 安全：操作权限+越权拦截 |

**复制类：**

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证复制功能正确性 | 字段继承/清空规则：主键清空、业务字段继承 |
| 验证复制后独立编辑不影响原数据 | 数据隔离：修改副本不影响源记录 |
| 验证复制功能权限控制 | 安全：操作权限+越权拦截 |

### 5.2 查询/列表类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX列表展示 | 默认视图、字段来源/展示格式、数据完整性 |
| 验证XX筛选搜索功能 | 快捷筛选、高级搜索、多条件组合查询 |
| 验证XX详情展示 | 默认详情查看、只读不可编辑 |
| 验证XX取数逻辑 | 多种业务条件下的数据提取验证 |
| 验证XX权限过滤 | 数据可见范围、越权防护 |

### 5.3 导入/导出类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX数据导出功能正确性 | 不同文件格式、文件内容、格式、字段完整性 |
| 验证XX数据导入功能正确性 | 不同文件格式、模板下载、数据校验、导入成功/失败处理 |
| 验证导入数据异常时的错误提示 | 格式错误、重复数据、必填项缺失的定位和提示 |

### 5.4 审核/审批类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX审核功能 | 正向审核通过、每个节点拒绝处理、每个审核节点的定义 |
| 验证XX权限控制 | 审核人身份校验、越权拦截 |
| 验证XX审批流转规则 | 多节点流程组合（会签/或签/驳回/撤回/转交） |

> 如涉及审批流程，还需参照《通用测试规则》§2.4 中的审批流程专项覆盖。

### 5.5 同步/定时任务类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX同步功能 | 触发时机、执行频率、同步结果正确性 |
| 验证XX异常处理 | 幂等性、漏同步纠正、失败重试 |
| 验证XX业务逻辑 | 多场景下的业务逻辑处理 |

### 5.6 配置/参数管理类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX开关配置生效 | 打开/关闭两种状态的功能差异 |
| 验证XX字典/码值配置正确性 | 配置变更后前端展示更新 |
| 验证XX参数配置生效 | 参数修改后的业务逻辑变化 |
| 验证XX页面组件配置 | 菜单、落地页、顶部组件等的可配置性 |

### 5.7 消息/通知类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX消息推送触发正确性 | 满足条件时是否发送、不满足时不发 |
| 验证XX消息接收人和内容准确性 | 接收人角色、消息内容、短链跳转地址 |
| 验证XX消息推送渠道 | 短信/邮件/站内信/飞狼等各渠道 |
| 验证XX消息不重复推送 | 同一事件不重复发送 |

### 5.8 数据展示与核对类

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX列表/详情数据展示准确性 | 字段来源、关联数据展示、空值处理 |
| 验证XX数据同步/回写正确性 | 源系统与目标系统数据一致性 |
| 验证XX统计/汇总指标计算准确性 | 合计、同比、环比、占比等聚合逻辑 |
| 验证XX接口必填字段校验正确性 | 必输项为空时拦截 |
| 验证XX接口字段长度/格式/枚举校验 | 超长、格式非法、非枚举值时拦截 |

### 5.9 账务处理类

**清算/入账处理类：**

| 测试点 | 用例关注重点 |

| 验证XX清算周期入账正确性 | 分业务场景，含本行/他行渠道差异 |

| 测试点 | 用例关注重点 |

| 测试点 | 用例关注重点 |

**冲正/反交易类：**

| 测试点 | 用例关注重点 |
|--------|-------------|
| 验证XX交易冲正/反交易主流程 | 冲正触发条件和执行流程 |

## 六、测试点生成工作流程

按以下步骤执行：

### 步骤 1：理解需求

识别需求的测试重点内容：

| 识别项 | 说明 |
|--------|------|
| **核心业务目标** | 需求主要要实现什么功能或什么主业务流程？ |
| **核心业务逻辑** | 实现需求目标的操作功能、关键判断、逻辑规则是什么？有无复杂业务规则？ |
| **高风险点与异常分支** | 实现需求目标过程中容易出错或需要特殊处理的环节，核心业务流程的异常分支 |

**判断原则**：
- 新增功能：主流程和核心逻辑是重点
- 优化逻辑：优化后的逻辑分支和状态变化、主流程回归是重点
- 不要为了凑数生成无意义的测试点

### 步骤 2：确定维度组合

| 动作 | 参考文档 |
|------|---------|
| 判断业务场景类型 | 《测试维度定义》及其第三部分"维度选型指南" |
| 确定涉及的维度和小类 | 套用对应的大类→测试维度→小类组合 |
| 叠加业务特有规则 | 若用户提供了业务规则（资料形式），按提供的规则展开；未提供则不叠加，缺项走澄清 |

### 步骤 3：拆分功能点

按第二章的规则将需求拆分为独立、可测试的功能点：

1. 先拆大类模块（按业务域）
2. 再拆子功能（按系统操作能力）
3. 拆到叶子功能点（最小独立操作单元）
4. 如有跨模块全局场景，增设"业务流程场景"节点

### 步骤 4：提取测试点

对每个叶子功能点：

1. **匹配模板**：从第五章模板库中找到最接近的功能类型模板
2. **套用规则**：结合《通用测试规则》对应维度的关注点；若用户提供了业务规则，一并参考用户规则
3. **按需裁剪**：根据需求实际情况增删调整，不要机械全覆盖
4. **区分类型**：功能级测试点挂在叶子功能点下；场景级测试点按挂载规则放置
5. **去重**：同一逻辑只在一个地方验证，功能级和场景级互斥

### 步骤 5：全集覆盖自检

对每个叶子功能点，按以下清单检查其测试点集合是否构成"概念上的全集"：

| 检查项 | 说明 |
|--------|------|
| (a) 正向流程 | 是否有覆盖？（主路径能否走通） |
| (b) 反向/异常流程 | 是否有覆盖？（失败、拒绝、拦截、边界） |
| (c) 独立业务规则 | 是否有遗漏需求中明确定义的独立业务规则？（对照需求文档） |
| (d) 臆造检查 | 是否有臆造需求未定义的内容？（如有则删除或标注"待核验"） |
| (e) 过度拆分 | 是否存在可以用一条测试点概括却被拆成多条的情况？（合并） |
| (f) 过度合并 | 是否存在一条测试点涵盖多个独立规则的情况？（拆分） |

不满足上述任一条件时，回到步骤 4 调整。

### 步骤 6：组织排序

同一功能点下，按以下优先级从上到下排列：

| 优先级 | 内容 |
|--------|------|
| (1) | **正向流程**：主流程、标准场景的场景级测试点或标准正向的功能级测试点 |
| (2) | **核心逻辑与状态**：关键判断、逻辑分支、降级逻辑、状态流转的场景级测试点 |
| (3) | **异常处理**：失败场景、错误提示、异常分支的测试点 |
| (4) | **边界值与数据校验**：数据格式、长度限制、特殊字符、空值等模块级测试点 |
| (5) | **其他**：按需生成的性能、安全、UI 等非功能性测试点 |

**风格统一要求**：
- 测试点命名风格保持一致（均以"验证"开头，语言精简，不出现具体预期结果）
- 场景级测试点与功能级测试点在同一功能点下按上述逻辑分类排列，保障思路连贯性
- 功能点层级清晰，不要将不同层级的内容混杂

## 七、与两份规则文档（及用户业务规则）的配合关系

### 7.1 完整知识链

```
┌─────────────────────────────────────────────────────────────┐
│  附件1  测试维度定义                                          │
│  → 解决"从哪些维度测"                                        │
│  → 提供：大类→测试维度→小类三级骨架 + 维度选型指南            │
└──────────────────────────┬──────────────────────────────────┘
                           │ "按这些维度展开"
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  附件2  通用测试规则                                          │
│  → 解决"每个维度具体测什么"                                   │
│  → 提供：每个小类的详细关注点清单                              │
└──────────────────────────┬──────────────────────────────────┘
                           │ "有了规则，按以下方法写成测试点"
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  ★ 本文档  测试点生成指南                                     │
│  → 解决"测试点怎么写、长什么样、怎么从需求推导出来"             │
│  → 提供：概念定义 + 命名规范 + 模板库 + 工作流程 + 自检清单    │
└─────────────────────────────────────────────────────────────┘
```

**说明**：《测试维度定义》《通用测试规则》两份规则文档构成"主输入层"，用户以资料形式提供的业务规则为"补充输入"，本文档是"加工层"，负责将规则转化为结构化的测试点输出。

### 7.2 维度到测试点的映射路径

测试点生成的查找路径：

```
需求文档
  │
  ▼ ① 查附件1 → 确定涉及的维度组合
  │     例：增删改类操作 → 基础功能 + 界面与体验 + 权限控制
  │
  ▼ ② 查附件2 → 获取每个维度的关注点规则
  │     例：基础功能→字段校验，获取六大固定场景
  │
  ▼ ③ 参考用户业务规则 → 若用户以资料形式提供了业务规则，叠加使用；未提供则跳过本步
  │
  │     ── 以上①-③完成后，已具备完整的规则素材，进入测试点生成阶段 ──
  │
  ▼ ④ 按本文档方法论 → 把规则转化为结构化测试点
  │     ④a 拆功能点（第二章）
  │     ④b 命名测试点（第三章）
  │     ④c 套模板库（第五章）
  │     ④d 控颗粒度（第四章）
  │
  ▼ ⑤ 按本文档第六节自查 → 全集覆盖检查
```

### 7.3 按需选择策略

| 原则 | 说明 |
|------|------|
| 不机械全覆盖 | 根据需求分析结果只输出实际涉及的测试类别和子项；未涉及的部分直接省略 |
| 模板按需裁剪 | 第五章模板提供参考颗粒度，需求不涉及模板中某类型的，根据命名规范和颗粒度自行推导 |
| 业务规则按需叠加 | 若用户提供了业务规则（资料形式），按其内容按需叠加使用；未提供时不叠加、不臆造 |
| 界面检查按需输出 | 仅当需求涉及前端界面时才输出 UI 相关测试点；纯接口或批量作业需求省略 |

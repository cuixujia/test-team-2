# 资料质检判据

静态评审口径：对索引逐条对照下表检查项。检查方法见知识① §4.1「检查表（Inspection）」行，方法细节不在此展开。

## 检查项

| # | 检查项 | 判定 | 分级 |
|---|--------|------|------|
| 1 | 索引完整性 | 圈定范围相关的原文内容（章节、表格、规则段落）未被索引收录 → 问题 | 阻塞 |
| 2 | 索引准确性 | 索引条目锚点指向的位置与章节不符、行区间越界 | 阻塞 |
| 3 | 概要失真 | 概要与原文语义不一致（概要规范见 `test-knowledge-canon` §五） | 重大 |
| 4 | 范围覆盖 | scope 选中功能的相关内容无法通过索引检索到 | 阻塞 |
| 5 | docx/xlsx 锚点可靠性 | docx 无 Heading 章节结构、xlsx 无可用 Sheet/单元格 → 记问题；无法建立可靠锚点的，另开澄清问题 | 阻塞 |
| 6 | 资料内部矛盾 | 不同资料间对同一事项描述冲突 → 记问题并开澄清 | 重大 |
| 7 | 索引冗余 | 与圈定范围明显无关的索引条目 | 一般 |
| 8 | 待澄清资料缺口 | 选中功能的需求文档没描述四份原文知识链里应测的测试维度、小类或关注点（如字段长度）却未登记 → 记问题并汇入「待澄清资料缺口」表 | 一般 |

索引类问题的核查结果汇入报告模板「问题清单」表；资料描述缺口类汇入「待澄清资料缺口」表；概要质量的最低要求见 `test-knowledge-canon` §五。

锚点抽验：md/txt/csv 直读原文比对行区间；docx/xlsx 与命令写法按 `citation-verify`「QA 抽验」节执行。

## 待澄清问题四要素

影响 TP/TC 生成的歧义点，每条必含：

| 字段 | 要求 |
|---|---|
| 问题 | 一句话说清歧义，附着证据锚点 |
| 影响面 | 波及哪些功能/维度/可能的 TP |
| 默认建议 | 具体可执行、可直接转成断言口径；不可执行的不算默认建议（必须有，不许空） |
| 来源 | 材料的锚点位置 |

**一条只写一个点**：一行（一个编号）只写一个待澄清的歧义点。

产生澄清问题的典型情形：需求与设计描述冲突、业务流程/权限/结果等关键规则缺失、术语多义、docx/xlsx 无法建立锚点、原文检索定位失败。**测试维度、小类或关注点的描述缺失不在此列，走「待澄清资料缺口清单」**。

## 待澄清资料缺口清单

阶段 2 的第二道澄清按 `test-knowledge-canon` 知识清单所引四份原文反查资料：需求文档只写了某个功能/对象（如「表单有姓名字段」），却没写知识链要求测的测试维度、小类或关注点（如「字段长度」）——这类「知识库要测、资料里没描述」的内容按测试点汇总登记，供关口 2 决策「补充资料 / 静默生成」。这是资料描述缺口，不判资料不合格、不阻塞收敛。

### 反查路径（四份原文的知识链，见 ④§7.1 / §7.2）

1. **定测试点**：以 scope 选中功能下的一个具体测试点/验证对象为单位（如「F01 需求新增表单字段校验」「F02 需求列表查询」），按 ②§三 维度选型指南判断其业务场景类型，套用「大类 → 测试维度 → 小类」组合；按 ②§二 明细表逐小类读「定义 / 关注点 / 典型场景举例」判定适用性。不落基线产物、不与生成端互相否决（口径见 `test-point-workflow` 方法链第 1 步与质检判据 5）。
2. **拿关注点**：按 ③附录「与《测试维度定义》的对应关系」找到该小类对应章节，取详细关注点清单。例：「基础功能 / 字段校验」→ ③§1.2，含输入域四要素、六大固定场景（空 / 长度 / 数值 / 字符 / 格式 / 枚举）、判定规则、输入域联动、前后端校验一致性。
3. **对表原文**：逐项核对该测试点应测的每个小类/关注点，资料里有没有可支撑测试内容的描述；把所有没描述的项汇总到该测试点一行。除知识链列明的小类外，**按测试经验判断该功能还应测、资料却完全没提到的点**（如异常、并发、安全、边界等经验场景）也一并记入同一行。
4. **补法依据**：④§五 模板库给出该形态的展开方向，①§七 方法选型决策指南给出用例设计方法，用于说明「补了之后会怎么测」。

### 归组与写法

**一行一个测试点**：同一测试点下所有字段/对象、所有缺少描述的维度/小类/关注点合并成一条，逐项点名写进「缺少的维度/小类/关注点」列；不按「字段 × 小类」拆行，也不把不同测试点并成一行，更不许把多个测试点汇总成一条笼统问题。例：表单只写了姓名字段，该表单下各字段缺的长度、必填、字符、格式等小类算一个问题。

| 列 | 写法 |
|---|---|
| 编号 | `Q-M-R{n}-D{seq}`（如 `Q-M-R1-D1`）；一行一条，写入 `state/clarifications.md` 对应 C 编号的「来源」列 |
| 问题描述 | 只写「资料写了哪个测试点/对象 + 该测试点按《测试维度定义》应测而资料没描述」。不出现"引用"字样，不写知识库章节号、关注点原文摘抄、锚点与出处，不写「字段属性不明」式笼统结论 |
| 缺少的维度/小类/关注点 | 逐项点名该测试点未描述的测试维度、所属小类及关注点，按维度分组列全；含按测试经验判断应测而资料未提及的点；禁「等」「相关维度」式省略 |
| 默认建议 | 固定「静默生成：按四份原文知识链推导该测试点缺少的维度/小类/关注点的测试内容，仅写宽泛表述、不写具体值」 |

其他口径：

- 只登记测试维度/小类/关注点的描述缺失（含经验判断应测而资料未提及的点）；业务流程/权限/结果等业务规则缺失、资料矛盾、术语多义归「待澄清问题四要素」，不进本清单。
- 登记前须用对象锚点核实该测试点/对象在原文存在，锚点只用于核实、不写进本表；原文没有的功能/对象不得列入，后续也不得生成对应测试内容（边界见 `test-knowledge-canon` §四）。
- 用户选补充资料时，答复的资料描述写回 `state/clarifications.md` 对应 C 编号的「答复」列。

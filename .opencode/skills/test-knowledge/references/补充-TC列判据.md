# 补充件：TC 三列与 TP 命名词法判据

> **身份**：本文件是补充件，不是四份原文之一。内容 = 知识④§五模板库右列「用例展开关注重点」在 TC 三列（标题/测试数据/步骤/预期结果）的落位判据 + 知识④§三命名的两条词法补充。与原文冲突时以原文为准。
>
> 方法论（取什么值、按什么方法铺场景）不在本件复述：取值仍依知识③§1.2（输入域四要素、六大固定场景）与知识①§5.1.1/§5.1.2（等价类代表值、边界值六点）。

## 一、TC 三列判据

### 标题

- 结构 = **场景 + 预期落点**：以「场景…验证」收口式（如「编辑风险时上传空文件验证」）或「场景 + 预期」陈述式（如「金额超单笔限额，交易拒绝并提示」）承载均可。
- **一次判定原则**：一个标题只承载一次判定。预期结果可含多个观察点（如「余额不变 + 流水生成」），但须同属一次判定；承载第二种判定即拆分为两条用例。

### 测试数据

- 给**具体值**或可执行构造方法，金额/字段给到具体数值；禁止「系统正常」「适当数据」类可随意替代的表述。
- 值的选择按知识③§1.2 四要素/六场景、知识①等价类与边界点执行，本件不复述。

### 操作步骤

- **动词开头、编号分步**（「1.」与「1、」均可）；不含歧义词（「等一下」「适当输入」类禁用）。
- **业务等待例外**：等待对象为系统行为（定时任务触发、状态扭转、异步回调、消息到达）且后续步骤含该行为的可判定观察点时，写「等待/触发」合规；等待对象为执行者判断或无法判定的等待（「等一会」「稍候再看」）仍违规。

### 预期结果

- 具体到**可观察物**：数据值/一致性（值类判定）、界面元素状态（高亮/灰显/置灰）、提示文案、状态变更、消息推送内容五类承载形态任一；可直接判 pass/fail。
- 错误提示指向**具体字段与原因**，不用通用模糊提示（知识③§1.2 判定规则）。

## 二、TP 命名词法补两条（对知识④§三、§3.3 的补强）

- **验证词去重**：名内「验证」仅出现一次；`验证XX功能验证` 式词面重复判错（如「验证高级搜索功能验证」❌）。
- **过粗校正**（「验证XX功能」式，如「验证新增功能」）：仅当该 TP 的直属 TC 承载**两类及以上判定维度**（字段校验、落库、默认值、消息提醒等各自独立计）时判合规（TP 作为该业务能力的维度集），否则按知识④第4.1节「一条测试点涵盖多个独立规则→拆分」或过粗表现处置；不入下限词法硬规则（避免错杀）。
- 词面筛检的 PRD 原词豁免（补充件§二）同样适用本节两条。

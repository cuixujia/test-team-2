## 一、什么是测试

**软件测试（Software Testing）** 是一种通过手动或自动的方式，运行或检查系统及其相关组件，验证其是否满足**指定需求**、并识别**实际结果**与**预期结果**之间差异的系统性活动。

### 核心定义

> **测试不是证明软件没有缺陷，而是证明软件存在缺陷。** —— Glenford J. Myers

测试的本质是**风险驱动的探索活动**。我们无法穷尽所有可能的输入和路径，因此测试的目标是在有限的时间和资源内，发现尽可能多的严重问题，并对软件质量做出有依据的判断。

### 测试的两个关键视角

| 视角 | 关注点 | 典型问题 |
| ------ | ---------------------------- | ---------------------------- |
| **验证（Verification）** | "我们是否在正确地构建产品？" | 代码是否符合设计？ |
| **确认（Validation）** | "我们是否构建了正确的产品？" | 产品是否满足用户的真实需求？ |

## 二、测试的目的

测试不是单一目标，不同角色/阶段关注点不同：

### 2.1 核心目标

1. **发现缺陷（Find Defects）**
   - 暴露软件与需求、设计、用户期望不一致的地方。
   - 缺陷：Bug / 错误 / 偏差 / 缺失。

2. **验证与确认（Verification & Validation）**
   - **Verification**："我们是否正确地构建了产品？"（符合规格说明）
   - **Validation**："我们是否构建了正确的产品？"（满足用户真实需求）

3. **质量评估（Quality Assessment）**
   - 给出系统质量状态的可量化/可感知信息，支撑发布决策。
   - 如：缺陷密度、覆盖率、通过率、可靠性指标。

4. **降低风险（Risk Mitigation）**
   - 提前暴露关键路径上的问题，避免上线后造成更大损失。

5. **预防缺陷（Defect Prevention）**
   - 通过测试左移（TDD/评审/静态分析），减少缺陷注入

### 2.2 关于"测试能否证明无错"

- **测试只能证明存在缺陷，不能证明不存在缺陷**（Dijkstra）。
- 穷举测试在绝大多数系统中不可行，测试是**抽样 + 风险聚焦**的活动。

## 四、测试技术分类

按是否查看代码/内部实现，测试技术分为两大类：

### 4.1 静态测试（Static Testing）

**不运行程序**，通过评审/分析发现缺陷。

| 技术 | 说明 | 示例 |
| --- | --- | --- |
| 代码评审（Code Review） | 人工阅读代码找问题 | 同事审查 PR 中的空指针风险 |
| 静态分析（Static Analysis） | 工具扫描代码结构 | SonarQube 检测未关闭资源 |
| 走查（Walkthrough） | 作者讲解，他人提问 | 设计文档走查 |
| 检查表（Inspection） | 基于清单的正式评审 | 需求规格说明书审查 |
| 结对编程 | 边写边审 | 两人一机实时互相检查 |

### 4.2 动态测试（Dynamic Testing）

**运行程序**，输入数据观察输出。

#### 4.2.1 黑盒测试（Black-Box / 功能测试）

不关注内部实现，基于输入/输出行为测试。

- 依据：需求规格、用户故事、API 文档。
- 关注：功能正确性、接口契约、业务规则。

#### 4.2.2 白盒测试（White-Box / 结构测试）

基于代码内部结构、逻辑路径设计用例。

- 依据：源代码、控制流图、数据流图。
- 关注：语句覆盖、分支覆盖、路径覆盖、条件覆盖。

#### 4.2.3 灰盒测试（Gray-Box）

结合黑盒与白盒：了解部分内部结构，但仍以外部接口为主要测试点。

- 典型场景：集成测试、数据库相关测试、微服务测试。

### 4.3 手段对比总结

| 维度 | 黑盒 | 白盒 | 灰盒 |
| --- | --- | --- | --- |
| 视角 | 外部行为 | 内部逻辑 | 内外结合 |
| 设计依据 | 规格说明 | 源代码 | 架构 + 接口 |
| 适用级别 | 系统/验收 | 单元 | 集成 |
| 优势 | 贴近用户、语言无关 | 覆盖深入、发现隐藏缺陷 | 兼顾效率与覆盖 |
| 劣势 | 覆盖路径有限 | 成本高、语言相关 | 需一定内部知识 |

## 五、测试方法详解

以下方法可横跨不同级别与手段使用，是测试设计的核心工具箱。

### 5.1 黑盒测试方法

黑盒测试将系统视为"黑盒子"，只关心输入和输出，不关注内部实现。

#### 5.1.1 等价类划分（Equivalence Partitioning）

**核心思想**：将输入域划分为若干等价类，每类中选一个代表性值进行测试。如果一类中的一个值能通过/失败，假设该类中其他值也会同样通过/失败。

**步骤：**

1. 识别输入条件
2. 对每个条件划分有效等价类和无效等价类
3. 为每个等价类编号
4. 设计测试用例，尽量让一个用例覆盖多个未覆盖的有效等价类
5. 为每个无效等价类单独设计测试用例

**示例：年龄输入框，要求 18-60 岁**

| 等价类编号 | 类型 | 范围 | 代表值 | 预期结果 |
| --- | --- | ----------- | ------ | -------------------- |
| EP1 | 有效 | 18 ≤ x ≤ 60 | 30 | 接受 |
| EP2 | 无效 | x < 18 | 10 | 拒绝，提示"年龄不足" |
| EP3 | 无效 | x > 60 | 70 | 拒绝，提示"年龄超限" |
| EP4 | 无效 | 非数字 | "abc" | 拒绝，提示"格式错误" |
| EP5 | 无效 | 空值 | "" | 拒绝，提示"不能为空" |

**适用场景：**

- 表单字段验证
- 数值范围校验
- 枚举值选择

#### 5.1.2 边界值分析（Boundary Value Analysis）

**核心思想**：大部分缺陷发生在输入的边界上，因此重点测试边界值和边界附近的值。

**规则：**

- 对于范围 [min, max]，测试：min-1、min、min+1、max-1、max、max+1
- 即对每个边界取"刚好低于"、"刚好等于"、"刚好高于"三个值

**示例：密码长度要求 8-20 位**

| 测试值 | 位置 | 预期结果 |
| --- | ----- | -------- |
| 7 位 | min-1 | 拒绝 |
| 8 位 | min | 接受 |
| 9 位 | min+1 | 接受 |
| 19 位 | max-1 | 接受 |
| 20 位 | max | 接受 |
| 21 位 | max+1 | 拒绝 |

**适用场景：**

- 数值范围输入
- 列表分页（第 1 页、最后一页、超出页码）
- 文件大小限制
- 字符长度限制

#### 5.1.3 决策表技术（Decision Table）

**核心思想**：当多个条件的组合决定不同行为时，用表格形式列出所有条件组合及其对应动作。

**组成：**

- **条件桩**：所有输入条件
- **条件项**：各条件的取值（Y/N 或具体值）
- **动作桩**：所有可能的动作
- **动作项**：每种组合下执行的动作

**示例：贷款审批规则**

| 规则 | R1 | R2 | R3 | R4 | R5 |
| --- | ---- | ---- | ---- | ---- | ---- |
| 信用分 ≥ 700 | Y | Y | Y | N | N |
| 收入 ≥ 1万/月 | Y | N | Y | Y | N |
| 有逾期记录 | N | N | Y | N | N |
| **动作** | | | | | |
| 批准贷款 | ✓ | ✓ | ✗ | ✗ | ✗ |
| 人工审核 | ✗ | ✗ | ✓ | ✓ | ✗ |
| 拒绝申请 | ✗ | ✗ | ✗ | ✗ | ✓ |

**适用场景：**

- 业务规则复杂的系统
- 多条件组合决定结果的场景
- 金融、保险、审批类系统

#### 5.1.4 状态迁移图（State Transition Testing）

**核心思想**：系统根据当前状态和输入事件转移到新状态，测试各种状态迁移路径的正确性。

**示例：订单状态机**

```
         创建订单
   ┌─────────────┐
   ▼             │
[待付款] ──付款成功──→ [已付款] ──发货──→ [配送中]
   │                    │                     │
 超时                  取消                   签收
   │                    │                     │
   ▼                    ▼                     ▼
[已取消]            [退款中] ──退款完成──→ [已退款]    [已完成]
```

**测试要点：**

- 合法迁移：待付款 → 已付款 → 配送中 → 已完成
- 非法迁移：待付款 → 已完成（跳过中间状态）
- 边界迁移：超时自动取消、配送中取消触发退款
- 循环迁移：退款失败重新退款

**适用场景：**

- 工作流系统
- 订单/工单/审批流程
- 有明确生命周期的实体

#### 5.1.5 因果图（Cause-Effect Graphing）

**核心思想**：当多个输入条件之间存在 AND/OR/互斥等逻辑依赖时，有些组合根本不可能出现，通过因果图理清这些关系，剔除无效组合，只测有意义的场景。

**约束类型：**

- **E 约束（Exclusive）**：a、b、c 最多一个为 1（互斥，如支付方式只能选一种）
- **I 约束（Inclusive）**：a、b 至少一个为 1（至少选一个）
- **O 约束（Only-one）**：a、b 恰好一个为 1（二选一）
- **R 约束（Requires）**：a=1 则 b 必须为 1（前置依赖，如先登录才能下单）

**示例：注册账号功能**

| 条件 | 说明 |
|------|------|
| A：用户名不为空 | 必填 |
| B：密码 ≥ 8位 | 必填 |
| C：勾选用户协议 | 必填 |
| D：邮箱格式正确 | 必填 |

四个条件必须同时满足才注册成功；任一不满足就返回对应错误提示。不用因果图时，2⁴ = 16 种组合中有大量无效场景（如用户名为空时再去测密码长度无意义）；用因果图可精简为 5 条核心用例（全满足 + 各缺一项）。

**适用场景：**

- 输入条件之间存在复杂逻辑依赖（AND/OR/互斥/前置）
- 需要避免不可能的条件组合
- 与决策表结合使用效果更佳

#### 5.1.6 正交实验设计（Orthogonal Array Testing）

**核心思想**：当多个因素的全排列组合会导致用例爆炸时，用正交表选取最少量的代表性组合，保证**每两个因素的所有搭配都出现过至少一次**，即可发现绝大多数缺陷。

**示例：Web 兼容性测试**

涉及 4 个因素，每种 3 个取值：

| 因素 | 取值 |
|------|------|
| A. 浏览器 | Chrome、Firefox、Safari |
| B. 操作系统 | Windows、macOS、Linux |
| C. 分辨率 | 1080p、2K、4K |
| D. 网络环境 | WiFi、4G、弱网 |

- **全组合**：3⁴ = **81 种**
- **L9 正交表**：只需 **9 个用例**即可覆盖所有两两组合

| 用例 | A浏览器 | BOS系统 | C分辨率 | D网络 |
|------|---------|---------|---------|-------|
| TC1 | Chrome | Windows | 1080p | WiFi |
| TC2 | Chrome | macOS | 2K | 4G |
| TC3 | Chrome | Linux | 4K | 弱网 |
| TC4 | Firefox | Windows | 2K | 弱网 |
| TC5 | Firefox | macOS | 4K | WiFi |
| TC6 | Firefox | Linux | 1080p | 4G |
| TC7 | Safari | Windows | 4K | 4G |
| TC8 | Safari | macOS | 1080p | 弱网 |
| TC9 | Safari | Linux | 2K | WiFi |

验证：以 A×B 为例，Chrome/Firefox/Safari 分别与 Windows/macOS/Linux 的搭配在 9 条用例中全部覆盖到，其他因素对同理。

**适用场景：**

- Web 兼容性测试（浏览器 × 操作系统 × 分辨率）
- 多参数接口的组合测试
- 配置项众多的系统
- 表单多字段的下拉/复选框各种搭配

#### 5.1.7 场景法测试（Scenario Testing）

**核心思想**：基于真实用户使用场景设计测试，覆盖基本流（Happy Path）和各种备选流（Alternative Path）。

**示例：电商购物场景**

```
基本流（Happy Path）：
  浏览商品 → 加入购物车 → 结算 → 填写地址 → 选择支付 → 支付成功 → 查看订单

备选流：
  A. 购物车中有缺货商品 → 提示移除后继续结算
  B. 优惠券过期 → 提示优惠不可用
  C. 库存不足 → 提示下单失败
  D. 支付超时 → 订单进入待付款倒计时
  E. 新用户首次购买 → 弹出新人专享优惠
```

**适用场景：**

- 端到端业务流程验证
- 用户体验测试
- 验收测试设计

#### 5.1.8 错误推测法（Error Guessing）

**思想**：基于经验/直觉/历史缺陷，猜测系统易错点，针对性构造用例。

**常见猜测点：**

- 除零、空值、null、空集合
- 边界值、超长字符串
- 并发竞争、重复提交
- 权限越界、特殊字符注入

**适用场景**：**补充测试**，配合其他系统化方法使用，依赖测试者经验。

#### 5.1.9 探索性测试（Explorative Testing）

**思想**：同时设计用例与执行测试，**边学边测**，强调测试者的主动性、创造性与即时反馈。

**特点**：无固定脚本、依赖测试者技能、适合发现非常规缺陷。

**适用场景：**

- 时间紧、需求不稳定
- 发现 UI/体验/逻辑类缺陷
- 对新功能快速摸底
- 作为脚本测试的补充

### 5.2 白盒测试方法

白盒测试需要了解程序的内部结构和代码逻辑，通过设计输入使特定代码路径被执行。

#### 5.2.1 语句覆盖（Statement Coverage）

**定义**：确保程序中每条可执行语句至少被执行一次。

**示例：**

```python
def classify_score(score):
    if score >= 90:           # S1
        result = "优秀"       # S2
    elif score >= 60:         # S3
        result = "及格"       # S4
    else:                     # S5
        result = "不及格"     # S6
    return result             # S7
```

| 测试用例 | 输入 | 覆盖语句 |
| --- | -------- | ---------- |
| TC1 | score=95 | S1, S2, S7 |
| TC2 | score=75 | S3, S4, S7 |
| TC3 | score=45 | S5, S6, S7 |

→ 三条用例覆盖全部语句。

**局限性**：条件判断可能只走了一边，隐藏分支逻辑的 bug。

#### 5.2.2 判定覆盖 / 分支覆盖（Decision/Branch Coverage）

**定义**：确保每个判定的"真"和"假"分支都至少执行一次。

**续上例：**

| 测试用例 | 输入 | if≥90 | elif≥60 | 覆盖分支 |
| --- | ---- | ----- | ------- | ------------- |
| TC1 | 95 | True | - | 真分支(S1-S2) |
| TC2 | 75 | False | True | 假分支(S3-S4) |
| TC3 | 45 | False | False | 假分支(S5-S6) |

→ 每个判定真假都覆盖了。

**注意**：分支覆盖强于语句覆盖，但不保证所有条件组合都被测试。

#### 5.2.3 条件覆盖（Condition Coverage）

**定义**：确保复合判定中每个子条件的真假值都至少出现一次。

**示例：**

```python
if (age >= 18) and (has_id == True):  # 两个子条件
    allow_entry = True
```

| 测试用例 | age>=18 | has_id==True | 整体结果 |
| --- | ------- | ------------ | -------- |
| TC1 | True | True | True |
| TC2 | False | False | False |

→ 每个子条件的真假都出现了。

#### 5.2.4 判定-条件覆盖（Decision-Condition Coverage）

**定义**：同时满足判定覆盖和条件覆盖的要求。

**示例：**

```python
if (A and B) or C:
    do_something()
```

需要覆盖：

- A=T/B=T/C=T → 整体 True
- A=F/B=F/C=F → 整体 False
- A=T/B=F/C=F → 整体 False（A真B假）
- A=F/B=T/C=T → 整体 True（C真）

#### 5.2.5 路径覆盖（Path Coverage）

**定义**：覆盖程序中所有可能的执行路径。

**注意**：如果有循环，路径数量可能是无限的。实践中通常限制循环展开次数。

**示例：**

```python
def calc(a, op, b):
    if op == "+":          # 路径1
        return a + b
    elif op == "-":        # 路径2
        return a - b
    elif op == "*":        # 路径3
        return a * b
    elif op == "/":        # 路径4
        if b == 0:         # 路径4a
            return None
        return a / b       # 路径4b
    else:                  # 路径5
        raise ValueError()
```

共 6 条路径，需 6 个测试用例全覆盖。

## 六、测试级别与阶段

| 级别 | 对象 | 测试重点 | 常用方法 |
| --- | --- | --- | --- |
| 单元测试（Unit） | 函数/类/方法 | 逻辑分支、边界 | 白盒、参数化、TDD |
| 集成测试（Integration） | 模块/服务间接口 | 接口契约、数据流 | 灰盒、API 测试 |
| 系统测试（System） | 完整系统 | 功能/非功能需求 | 黑盒、场景法 |
| 验收测试（Acceptance） | 用户视角 | 业务需求满足度 | 黑盒、场景法 |

## 七、方法选型决策指南

| 需求/场景 | 推荐方法 |
| --- | --- |
| 输入有明确区间/枚举 | 等价类 + 边界值 |
| 业务规则多、条件组合复杂 | 判定表 / 因果图 |
| 端到端业务流程 | 场景法 / 流程分析 |
| 多因子配置组合（兼容性） | 正交实验 |
| 有状态机/状态转换 | 状态迁移测试 |
| 时间紧、需求变化快 | 探索性测试 |
| 补充常规方法遗漏 | 错误推测 |

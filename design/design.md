# 测试 Agent 团队设计

> 本文档为最初草案（含待补充占位）。方案定稿见 `design/design-v1.md`；运行时工作空间结构见 `design/工作空间目录结构.md`。

基于opencode的harness架构实现该测试agent团队

## 目标
这是一个测试 Agent 团队，目标是：由测试专家、测试质检专家两方协作，从用户提供的资料（需求文档、开发设计文档等，md/txt/csv/docx/excel 等）生成有依据、可追溯、可执行的测试点（TP）和测试用例（TC）。

## 角色的分工（写权限严格隔离）
Agent	                     角色	      职责
test-expert（测试专家）	编排者及生成者	流程主控、范围确认、澄清登记、状态簿、唯一面向用户的确认关口、生成TP、生成TC
test-qa-expert（质检专家）	质量检查者	    独立质检，只检不修，结论写入唯一 QA 报告

## 核心工作流
1. 确认范围 - 测试专家
1.1 用户指定若干个资料，通读PRD，识别本期需求设计哪些“业务功能”（PRD中会显性指明，若未指明则先行按理解识别，后在用户选择范围时让用户先确认再选范围），以清单形式让用户选择（可选1个或多个）
1.2 一次性让用户选择业务功能范围后，生成范围确认单（scope.md，写清全量清单及被选中的）
1.3 基于刚才通读的上下文记忆（不重复读取浪费token和时间），生成一份与所选业务功能相关的内容索引（相关的目录，及每个目录内容的概要，作为后续流程的快速检索入口，仅需读取这份文件，即可知晓所关注内容在哪份文件的哪个位置）。同时并行通读其它资料（每个资料一个并行）并生成对应的内容索引。每生成一份即交给测试专家落盘到一份“资料索引文档”中（追加形式）

2. 资料质检 - 质检专家
2.1 资料索引文档质检 - 根据用户圈定的业务功能，复盘资料索引文档有无漏洞、错误等（通读资料），并记录在质检报告中，并交给经理修复。【质检方法来自某skill，待补充1】
2.2 对资料索引文档修复结果复盘，直至不存在漏洞及错误。（最多3轮，否则交给用户抉择）
2.3 基于刚才通读的上下文记忆（不重复读取浪费token和时间。前提是opencode v1.x 支持复用前一次会话吗？），质检出影响TP、TC生成的待澄清问题，由经理交给用户做澄清
2.4 用户澄清后，将澄清结果落盘，作为后续的判定依据和tp/tc可追溯的依据

3. 测试点生成及修复 - 测试专家
3.1 根据“选定范围”和“资料索引”，快速定位原文出处，依据【相关skill，待补充2】识别出对应测试点，形成测试点清单（每个测试点能对应原文出处，可对应多处出处，每个出处照抄原文中最能体现测试点的不超过50字，超出部分用...）并落盘
3.2 指派质量专家做质检
3.3 对质检结果做修复

4. 测试点质检 - 质检专家
4.1 根据“选定范围”和“资料索引”，快速定位原文出处，依据【相关skill，待补充2】检查测试点清单有无漏洞、错误等，并记录在质检报告 
4.2 交由经理修复
4.3 对修复结果复盘，直至不存在漏洞及错误。（最多3轮，否则交给用户抉择）

5. 用户验收测试点 - 用户
5.1 用户查看测试点清单，进行对话调整或验收确认

6. 测试用例生成及修复 - 测试专家
6.1 根据“选定范围”、“资料索引”和“测试点清单”，快速定位原文出处，依据【相关skill，待补充3】识别出对应测试用例，形成测试用例清单（每个测试用例能对应测试点及原文出处，可对应多处出处，每个出处照抄原文中最能体现测试用例的不超过50字，超出部分用...）并落盘
6.2 指派质量专家做质检
6.3 对质检结果做修复

7. 测试用例质检 - 质检专家
7.1 根据“选定范围”、“资料索引”和“测试点清单”，快速定位原文出处，依据【相关skill，待补充3】检查测试用例清单有无漏洞、错误等，并记录在质检报告 
7.2 交由经理修复
7.3 对修复结果复盘，直至不存在漏洞及错误。（最多3轮，否则交给用户抉择）

8. 用户验收测试用例
8.1 用户查看测试用例清单，进行对话调整或验收确认

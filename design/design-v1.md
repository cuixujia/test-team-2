# 测试 Agent 团队方案 · design-v1（定稿）

> 本文件是团队方案的唯一权威定稿。最初草案见 `design/design.md`，运行时工作空间结构见 `design/工作空间目录结构.md`。
> 各类文件的模板唯一权威在对应 skill（见 §6），本文件只定结构与字段清单，不复述模板，防止两处漂移。

---

## 1. 目标

用户投入一批资料（PRD、开发设计文档；md/txt/csv/docx/xlsx），团队产出**有原文依据、逐条可追溯、可直接执行**的测试点（TP）与测试用例（TC）。中途用户仅需出面 **4 个关口**：选范围、答澄清、验收 TP、验收 TC（另有例外升级通道）。

## 2. 团队与写权限

| Agent | 角色 | 唯一职责 | 可写 | 不可写 |
|---|---|---|---|---|
| **test-expert** | 常驻主编排 + 唯一生成者 | 流程主控、范围确认、澄清登记、状态簿、生成 TP/TC、唯一面向用户 | scope/、state/、output/tp/、output/tc/ | output/reports/ |
| **qa-expert** | 独立质检（按需召唤） | 只检不修，三份质检报告的唯一写入者 | 仅 output/reports/ 三份报告 | 其余一切 |

写权限用 opencode V2 `permissions` 有序规则实现（**最后匹配生效**，宽规则在前、例外在后）：

- test-expert：可启动的子 agent 仅限 `qa-expert`（定义于 `.opencode/agent/qa-expert.md`，派发名唯一）；禁止写 reports/。
- qa-expert：先全量 deny，再例外放行——read/glob/grep 全放行；`edit` 与 `write` 均仅放行 `**output/reports/**` 路径（两级通配，兼容 file/<session>/**/output/reports/）；`shell` 仅放行 `python3 *inspect_anchor.py*`（只读锚点检视脚本，脚本本身零写入能力）；skill 加载放行；其余（edit/write 其他路径、shell 其他命令、question、subagent、webfetch/websearch）全部拒绝。权限在 subagent 会话建立时固化：改权限配置后必须新开会话重派。

辅助机制（不是替代）：每轮 QA 结束后，测试专家抽查 reports/ 之外关键文件未被改动并记入 state.md 实施日志。

**V0 验证项**（实施第一步）：确认运行环境 opencode 版本支持 V2 agent 语法（`.opencode/agent/*.md` frontmatter `permissions` 列表）；实测 QA 写 reports/ 放行、写 tp/list.md 被拦、`inspect_anchor.py` 可跑、其余 shell 被拦。若版本为 V1 语法，按 opencode 迁移说明改写 frontmatter 字段名，其余设计不变。

## 3. 架构铁律

1. **文件即状态（SSOT）**：subagent 每次调用都是全新上下文，agent 之间只靠文件交接，不靠对话记忆。全文通读全流程仅 2 次（阶段1 测试专家、阶段2 QA），其后一律"查索引定位 → 精读相关片段"。断线续跑：新会话开始先读 state.md 恢复。
2. **写权限即机制**：见 §2，制衡由文件边界保证，不靠自觉。
3. **增量回路**：修复增量、复检增量；回路 ≤3 轮 + 收敛判定提前退出。

## 4. 运行时工作空间

工作空间根约定：优先 `/file/`；若运行环境无 `/file/`，则在本团队仓库根创建 `runtime-file/` 并沿用同一结构。测试专家在会话启动时把实际根写入 state.md。结构如下（详细格式见 `design/工作空间目录结构.md`）：

```text
<工作空间根>/
├── project-docs/                        # 用户原始资料，只读，不动一个字
└── session-<项目id>-<时间戳>/           # 一次会话 = 一套完整流程
    ├── user-input/                      # 用户补充上传（只读）
    ├── scope/
    │   ├── scope.md                     # 范围确认单
    │   └── resources-index.md           # 内容索引（检索 SSOT）
    ├── state/
    │   ├── state.md                     # 进度看板：阶段/轮次/待用户事项/结论摘要/实施日志
    │   ├── clarifications.md            # 澄清台账
    │   └── repair-log.md                # 修复对照表（测试专家写，QA 增量复检的输入）
    └── output/
        ├── tp/list.md                   # 测试点清单
        ├── tc/list.md                   # 测试用例清单
        └── reports/                     # 三份报告，各按轮次追加（## R1、## R2…），无汇总文件
            ├── qa-materials.md          # 资料索引质检（含待澄清问题清单章节）
            ├── qa-tp.md                 # 测试点质检
            └── qa-tc.md                 # 测试用例质检
```

产物文件一览与职责：

| 文件 | 写者 | 内容要点 |
|---|---|---|
| scope.md | 测试专家 | 全量业务功能清单 + 选中标记 + 识别依据锚点 |
| resources-index.md | 测试专家 | 每份资料 → 章节 → 锚点 + ≤50字概要 |
| state.md | 测试专家 | 当前阶段/轮次/待用户事项/各阶段结论摘要/实施日志 |
| clarifications.md | 测试专家 | 澄清问题、影响面、默认建议、答复、状态、影响条目 |
| repair-log.md | 测试专家 | 每轮修复对照表：问题编号 → 修复动作 → 牵动条目 |
| tp/list.md | 测试专家 | TP 清单（6 列：编号/关联业务功能/测试点名称/类型/澄清依据/出处锚点） |
| tc/list.md | 测试专家 | TC 清单（11 列：编号/关联业务功能/关联TP/用例名称/用例类型/前置条件/测试数据/操作步骤/预期结果/澄清依据/出处锚点） |
| qa-materials.md、qa-tp.md、qa-tc.md | QA | 按轮次追加的质检报告 |

不设 qa-summary；不建 scope/excerpts/（续跑靠 state.md 摘要，成本≈0）。

## 5. 出处锚点规范（全团队唯一格式）

每个 TP、TC 必须带出处锚点（可多个），QA 报告里的问题也用锚点给证据。格式：

| 原文类型 | 锚点格式 | 例 |
|---|---|---|
| md/txt/csv | `文件名:起始行[-结束行] => "摘抄"` | `prd1.md:12-15 => "客户名称长度不超过50个字符"` |
| docx | `文件名#章节标题 => "摘抄"` | `需求.docx#新增客户 => "保存成功后状态置为待审核"` |
| xlsx | `文件名#Sheet名!单元格 => "摘抄"` | `规则.xlsx#字段规则!B3 => "证件号不允许为空"` |

硬性规则：
- 摘抄 ≤50 字（从原文照抄，不含结尾截断符）；超出截断并以 `...` 结尾
- 摘抄允许包含半角双引号（本会话 TP-014 实测通过机验）；若 `inspect_anchor.py` 判格式非法，再改摘抄片段或换全角 `”`（以脚本实测为准，不做未经验证的书面强约束）
- 多个锚点写在一个单元格内，用 ` ;; ` 分隔
- docx/xlsx **不转 md**：机验采用"现场抽取、用完即弃"；工作空间不落任何转换件，引用对象始终是原文件
- 无法建立可靠锚点（如 docx 无章节结构）→ 升级为澄清问题，禁止硬凑

## 6. 四个仓库内 skill（薄壳：只写"步骤、产物格式、写到哪"，方法内容一律引用 skill `test-knowledge` 的 `references/` 原文）

| Skill | 用在哪 | 内容来源 |
|---|---|---|
| `test-knowledge`（含 references 四份原文 + 四份补充件） | 全阶段（测试专家生成、QA 质检共用判据） | 方法与判据唯一权威源；阶段产物格式白名单见补充《产物格式规范》 |
| `citation-verify` 引文机验 | 每次生成后、送检前（测试专家执行）；QA 抽验锚点用其只读检视脚本 | 自带 `scripts/`：`lib_citation.py`（核心）、`verify_citation.py`（全量校验，JSON 输出）、`inspect_anchor.py`（只读检视，零写入） |

机验校验五项：①锚点在原文真实存在（md 行号制、docx/xlsx 现场抽取制）②摘抄与原文匹配且 ≤50 字、截断规则正确 ③TC 的关联 TP 编号真实存在 ④澄清依据编号在 clarifications.md 中存在 ⑤TP/TC 编号格式合法。另输出**TP 覆盖缺口警告**（无 TC 关联的 TP，仅警告不拦截）。测试专家只调用、读结果；校验口径改动只改 skill 内脚本。目录与文件名按 §4 执行；模板细节以各 skill 为唯一权威。

## 7. 完整流程（6 阶段 + 2 贯穿机制）

### 阶段1 范围确认与建索引（测试专家）
1. 通读 PRD，识别业务功能清单（PRD 显性指明；未指明则按理解识别，先交用户过目再选）
2. 用户一次性多选 → 落盘 scope.md → 关口1
3. 基于通读上下文生成所选功能的内容索引；**并行**读其余资料逐份生成索引，追加进 resources-index.md

### 阶段2 资料质检与澄清（QA，全文通读 ×1）
QA 依据「资料质检」skill，单次通读双产出，全部写入 qa-materials.md：
- **产出① 索引质检**：对照原文查索引遗漏/锚点错误/概要失真/范围覆盖缺口/docx/xlsx 锚点可靠性 → 问题分级清单（R1）
- **产出② 待澄清问题**：影响 TP/TC 生成的歧义点，每条含"问题 + 影响面 + 默认建议"（R1 的专门章节）
- 之后：测试专家按修复清单**增量修复**索引并写 repair-log.md → QA 增量复检（回路骨架，≤3 轮）→ 待澄清问题整理落盘 clarifications.md（状态"待答复"）→ 交用户答复，可全答/部分答/不答 → 未答复的置"默认生效" → 关口2 完成

### 阶段3 测试点生成（测试专家）
- **输入四件套**：scope 选中项 + resources-index + clarifications + knowledge 方法链
- 方法链（见 skill `test-knowledge` 阅读路径）：维度选型 → 维度关注点 → 拆功能点 → 模板命名 → 颗粒度控制 → 排序
- 按业务功能**并行**生成片段再合并；生成后过六项自检（正向/反常/独立规则遗漏/臆造/过细/过粗）
- 落盘 tp/list.md：每条带锚点；澄清依据列填澄清编号，按默认建议生成的标 `(默认)`
- **机验不过不送检**：跑 verify_citation.py，failures 必须为 0 才能进阶段4

### 阶段4 测试点质检与用户验收
- QA 依据「测试点」skill 质检部分全量检（覆盖率定义见机制A）→ 写 qa-tp.md（R1）
- 回路骨架修复收敛 → **关口3 用户验收**：调整走小回路（测试专家改 → QA 单轮复检，不占 3 轮）或确认通过

### 阶段5 用例生成（测试专家）
- 输入四件套改为：scope + resources-index + clarifications + **tp/list.md**（不重读原文，TC 是 TP 的纯展开）
- 按方法选型（等价类/边界值/决策表/因果图/状态迁移/场景法/正交实验/错误推测）把每条 TP 展开为正/反/边界用例；每条 TP 基线衍生 2~3 条
- 落盘 tc/list.md；机验（含 TP 覆盖缺口警告的人工确认）过后才送检

### 阶段6 用例质检与用户验收
- QA 依据「测试用例」skill 质检部分全量检 → 写 qa-tc.md → 回路骨架修复收敛 → **关口4 用户验收**

### 机制A 质量回路骨架（阶段2、4、6 复用）
```
生成 → 机验前置（不过不送检）→ QA 全量检 → 问题分级（阻塞/重大/一般）
  → 测试专家增量修复，写 repair-log.md（问题编号 → 修复动作 → 牵动条目）
  → QA 增量复检（只核 repair-log 对应条目 + 新增条目）→ 收敛判定（无阻塞级问题即提前收工）
  → 满 3 轮未收敛 → 用户三选一：接受现状 / 指令修复 / 中止
```
- **"全量串行"= 覆盖率要求而非单次调用要求**：清单过大时按业务功能分批，QA 逐批连续检完、不重不漏，合并为一份当轮报告
- 修复产生的新条目入增量检；未触碰的条目绝不重检

### 机制B 澄清回路（贯穿全流程）
- 澄清可击中的修复范围 = **三项**：TP/TC 条目、索引条目、scope 选中项（例：用户答"该模块本期不上线"→ scope 去勾 + 索引标记 + 相关条目移除）
- 统一走：测试专家登记 → 增量修复三项 → QA 单轮局部重检（不占 3 轮）
- **默认策略**：未答复/漏答的澄清按默认建议执行；据此生成的条目标 `(默认)`；QA 对带此标记的条目重点核查

## 8. 用户 4 关口

| # | 时机 | 动作 |
|---|---|---|
| 1 | 阶段1末 | 选业务功能范围（一次性多选） |
| 2 | 阶段2末 | 批量答复澄清（可不答，默认生效） |
| 3 | 阶段4末 | TP 验收 / 对话调整 |
| 4 | 阶段6末 | TC 验收 / 对话调整 |
| 例外 | 3 轮未收敛、资料无法解读、范围外异常 | 测试专家升级给用户三选一 |

其余全程无需用户参与；state.md 随时可查进度。

## 9. 硬规则清单（违反即流程违规）

1. 测试专家产物送检前必须过机验，`failures` 非零不进质检
2. QA 只能写 reports/；QA 报告落盘后测试专家不得修改
3. 任何 TP/TC 条目必须带出处锚点；依赖澄清/默认的必须标注编号
4. 修复必须写 repair-log.md 对照表；复检只查对照表 + 新增条目
5. 测试专家产物禁止自检替代 QA
6. 索引定位失败、原文查不到 → 登记澄清问题，禁止臆造
7. docx/xlsx 无法建立可靠锚点 → 升级澄清，禁止硬凑
8. 澄清未答复按默认建议执行，条目标 `(默认)`，QA 重点核查

## 10. 快与稳（耗时 vs 质量总表）

| 环节 | 策略 | 结果 |
|---|---|---|
| 通读 | 全程仅 2 次（阶段1、阶段2） | 砍掉最大耗时项 |
| TP 生成 | 按业务功能并行 | 快 |
| TC 生成 | 基于 TP 纯展开，不重读原文 | 省一次通读 |
| TP/TC 质检 | 全量串行（覆盖率定义，允许分批多次调用） | 交叉问题不漏 |
| 修复/复检 | 全程增量 | 轮内不白跑 |
| 轮次 | ≤3 + 收敛提前 | 不机械空转 |
| 机验前置 | 脚本先筛低级错误 | QA 轮次只打真问题 |
| 续跑 | state.md 摘要 | 不断线、成本≈0 |

**不对称原则：生成走快路（并行、复用、不重读），质检走稳路（全量、收敛才放行）。**

## 11. 已知风险与接受项

| 项 | 性质 | 应对 |
|---|---|---|
| V0：opencode 版本/权限实测结果待确认 | 实施风险 | 首日验证；V1 语法则按迁移说明改写 frontmatter，其余设计不变 |
| QA 多阶段多次召唤、每轮重装上下文，token 随阶段线性叠加 | 接受成本 | 写权限隔离 + 独立质检换来的必然代价 |
| shell 按 `python3 *inspect_anchor.py*` 模式放行，理论上可被构造命令绕过 | 接受风险（低） | inspect 脚本零写入能力；QA 提示词硬约束；测试专家轮后抽查非 reports 文件未动并记入实施日志 |
| docx/xlsx 锚点可靠性弱于 md 行号 | 接受成本 | 现场抽取机验 + "无章节结构升级澄清"兜底 |

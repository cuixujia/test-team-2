# 业务需求说明书

## 一、需求背景

杭州银行各业务部门在系统建设过程中，存在大量系统建设需求需要通过科技/IT部门统一承接。当前需求管理面临以下核心问题：

1. **需求入口分散、缺乏统一归口**：各部门通过邮件、IM、线下等多种渠道提出系统建设需求，无法集中查看和统计，科技/IT部门难以全面掌握需求全貌。
2. **需求状态不透明**：业务方不清楚自己提出的需求进展到哪一步，需要频繁询问科技/IT部门，沟通成本高，影响业务协作效率。
3. **历史需求无法沉淀复用**：过往需求资料散落各处，新需求难以参考相似案例，存在重复建设的风险。

为系统性解决上述问题，拟建设「杭州银行系统需求管理平台」，面向科技/IT部门提供统一的系统建设需求管理能力，实现需求的统一受理、规范评审和进度透明跟踪。

## 二、需求目标

建设杭州银行系统需求管理平台，面向科技/IT部门提供统一的系统建设需求管理能力，实现以下核心目标：

1. **统一归口受理**：建立系统建设需求的统一入口，各业务部门通过平台集中提交需求，科技/IT部门统一受理、登记和分类，消除多渠道分散提报的问题。
2. **需求状态透明**：为业务部门和科技/IT部门提供需求处理进度的可视化视图，业务方可随时查看自己提交的需求当前处于哪个处理阶段，减少反复询问的沟通成本。
3. **规范需求评审**：建立结构化的需求评审流程，科技/IT部门对受理的系统建设需求进行可行性评估和需求澄清，确保需求在进入后续环节前质量可控。
4. **基础需求存档**：所有经平台受理的需求及其处理记录自动存档，形成可追溯的需求台账（本期不做历史需求知识库或相似案例推荐）。

## 三、需求范围

### 3.1 本期包含范围

| 功能模块 | 说明 |
| --- | --- |
| **需求统一受理** | 各业务部门通过平台统一入口提交系统建设需求，科技/IT部门集中接收。支持需求创建、信息登记（标题、描述、业务领域分类等），需求按业务领域归类管理。 |
| **需求评审** | 科技/IT部门对受理的系统建设需求进行可行性评估和需求澄清。通过 BRD 协作会话组织评审，评审通过后需求进入待派发状态。 |
| **需求派发与任务承接** | 评审通过的需求由科技/IT部门派发给具体的产品经理或技术负责人承接，形成待承接任务。承接人可确认承接、拒绝或转派任务。 |
| **技术功能点拆解** | 任务承接后，承接人将需求拆解为可独立开发的技术功能点，管理拆解状态（待拆解/已拆解），支持功能点绑定存量服务或函数资产、在拆解过程中新增服务，按迭代统计拆解进度。 |
| **需求进度跟踪** | 以泳道分组形式展示需求及关联任务在各处理阶段的状态分布，业务方可随时查询指定需求的完整处理进度。 |
| **需求工作台** | 为用户提供一站式工作全景视图，按泳道展示待沟通需求、待接收任务、处理中任务、待评审任务和已完成任务，并统计各工作空间的工作负载。支持按工作空间分组查看会话列表，直接进入 BRD/PRD 协作会话。（复用现有工作台信息展示能力） |
| **需求资产查询** | 支持按资产类型（BRD/PRD/FDD）和编号查询需求及其关联任务、功能的完整信息，包括领域标签、主题活动标签、价值链标签、相似资产列表和血缘关系结构。（复用现有研发资产查询、资产标签查询、资产血缘查询能力） |
| **待办信息查询** | 查询当前用户的待办事项列表，包括待承接任务、待评审任务等待办类型，支持按状态筛选和快速跳转处理。 |
| **基础需求存档** | 所有经平台受理的需求及其处理记录自动存档，形成可追溯的需求台账。 |

### 3.2 本期不包含范围

| 排除项 | 说明 |
| --- | --- |
| 排期规划 | 本期不做排期计划编制、甘特图或时间轴视图，仅做到需求受理和进度跟踪。 |
| 开发与交付环节 | 开发实施、测试验收、上线交付由其他系统承接，本平台不介入后续环节。 |
| 优先级评估机制 | 本期不引入统一的优先级评估规则或排序机制。 |
| 需求与项目/资源关联 | 本期不建立需求与具体项目、开发负责人、预计上线时间的映射关系。 |
| 历史需求沉淀复用 | 本期不做历史需求知识库、相似案例智能推荐，仅做基础的需求记录存档。 |

## 四、业务流程

### 4.1 主流程总览

```
业务部门提出需求 → 科技/IT统一受理归口 → 需求评审 → 需求派发与任务承接 → 技术功能点拆解 → 进度跟踪
```

### 4.2 各环节说明

#### 环节一：需求提出（业务部门）

- **参与角色**：业务部门用户（需求发起人）
- **操作内容**：业务部门通过平台统一入口创建系统建设需求，填写需求标题、描述、所属业务领域等基本信息。
- **触发条件**：业务部门有系统建设需求时。
- **完成标志**：需求创建成功，进入「待沟通」状态，系统生成需求 ID 和 BRD 协作会话。

#### 环节二：统一受理归口（科技/IT部门）

- **参与角色**：科技/IT部门产品管理人员（受理人/派发人）
- **操作内容**：
  - 集中接收各业务部门提交的系统建设需求，统一登记和分类。
  - 对需求进行业务领域归类，确保需求正确归属到相应业务领域。
  - 可修改需求标题、维护需求信息。
- **前置条件**：需求已由业务部门创建并进入「待沟通」状态。
- **完成标志**：需求完成受理登记和分类，进入「待评审」状态。

#### 环节三：需求评审

- **参与角色**：科技/IT部门产品管理人员（评审组织者）、相关技术负责人
- **操作内容**：
  - 通过 BRD 协作会话组织需求评审，对受理的系统建设需求进行可行性评估和需求澄清。
  - 评审过程中可补充需求细节、明确边界。
  - 评审通过后，需求上传最新版本的 BRD 文档，进入「待派发」状态。
- **前置条件**：需求已完成受理归口，处于「待评审」状态。
- **完成标志**：BRD 文档评审通过并上传最新版本，需求进入「处理中」状态。

#### 环节四：需求派发与任务承接

- **参与角色**：科技/IT部门产品管理人员（派发人）、产品经理或技术负责人（承接人）
- **操作内容**：
  - **派发**：派发人将评审通过的需求转化为具体工作任务，指定承接人（产品经理或技术负责人），任务进入「待承接」状态并向承接人发送待办通知。
  - **承接**：承接人确认承接任务，任务进入「处理中」状态；或拒绝任务（状态变为「已拒绝」）；或转派给其他人员。
  - **撤回**：派发人可撤回已派发的任务，任务状态变为「已撤回」。
- **前置条件**：需求已通过评审并上传最新 BRD 文档。
- **完成标志**：任务被承接人确认承接，进入「处理中」状态。

#### 环节五：技术功能点拆解

- **参与角色**：产品经理或技术负责人（承接人）
- **操作内容**：
  - 承接人将已承接的需求拆解为可独立开发的技术功能点，管理拆解状态（待拆解→已拆解）。
  - 功能点可绑定存量服务或函数资产，也可在拆解过程中新增服务。
  - 按迭代统计拆解进度，跟踪待拆解和已拆解的功能点数量。
- **前置条件**：任务已被承接人确认承接，进入「处理中」状态。
- **完成标志**：需求下的功能点拆解完成，所有功能点状态更新为「已拆解」。

#### 环节六：进度跟踪与查询

- **参与角色**：业务部门用户（需求发起人）、科技/IT部门产品管理人员、产品经理或技术负责人
- **操作内容**：
  - **需求进度查询**：业务用户根据需求 ID 查询该需求的完整处理进度，以泳道分组形式展示需求及关联任务在各阶段的处理状态。
  - **需求工作台**：用户登录后查看个人工作全景，按泳道分组展示待沟通需求、待接收任务、处理中任务、待评审任务和已完成任务，并可查看各工作空间的工作负载统计；左侧按工作空间分组展示会话列表，可直接进入 BRD/PRD 协作会话。
  - **需求资产查询**：用户按资产类型（BRD/PRD/FDD）和编号查询需求及其关联任务、功能的完整信息，包括领域标签、主题活动标签、价值链标签、相似资产列表和血缘关系结构。
  - **待办信息查询**：用户查询当前待办事项列表，包括待承接任务、待评审任务等待办类型，支持按状态筛选和快速跳转处理。
- **触发条件**：用户主动发起进度查询、访问工作台首页、查询资产信息或查看待办列表。
- **完成标志**：系统返回对应的进度列表、工作台概览、资产信息或待办列表数据。

### 4.3 需求状态流转

| 当前状态 | 可流转到 | 触发操作 |
| --- | --- | --- |
| 待沟通 | 待评审 | 科技/IT完成受理登记和分类 |
| 待评审 | 处理中 | BRD 评审通过并上传最新版本 |
| 处理中 | 已完成 / 已取消 | 所有关联任务完成 / 需求被删除 |
| 待承接（任务） | 处理中（任务） | 承接人确认承接 |
| 待承接（任务） | 已拒绝（任务） | 承接人拒绝任务 |
| 待承接（任务） | 已撤回（任务） | 派发人撤回任务 |
| 处理中（任务） | 待拆解（功能点） | 承接人开始技术功能点拆解 |
| 待拆解（功能点） | 已拆解（功能点） | 功能点拆解完成并绑定资产 |
| 已拆解（功能点，全部） | 已完成（任务） | 所有关联功能点拆解完成 |
| 处理中（任务） | 已完成（任务） | 业务审核通过 |
| 处理中（任务） | 业务已拒绝（任务） | 业务审核拒绝 |

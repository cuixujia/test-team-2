**一句话回答"为什么这么大"**：不是任务本身内容多（新增 input 仅 76 万），而是 **254 个 agent 回合 × 平均每回合 7.4 万 token 的上下文重发**。Agent 每执行一步都要把"系统提示 + 已读文件 + 历史对话"整体再发给模型一遍，这部分计入 cache_read，占了总量的 96%。所以下面所有优化点的本质都是两件事：**让上下文更小、让回合数更少**。

## 3. Token 大的六个根因（按影响排序）

### 3.1 【最大】逐条 edit 落盘：49 个"只含 1 次 edit"的回合，烧掉 435 万 token（占 23%）

TC 生成会话在写用例文件时，大量回合**一步只做一个 edit**。典型是 TC生成 B01 在 00:24:47→00:25:33 连续 **13 个单 edit 回合**，此时上下文已达 ~110K，等于每改一小段就把 11 万 token 重发一遍，仅这 13 步就 ≈143 万 token。

[test-manager.md](file:///d:/Project/test-team-2/.opencode_v2/agent/test-manager.md) 第 113 行对经理自己要求"每个节点先把该节点全部小节的改动收集齐，一次 edit 写完，禁止跨消息逐节拆分"，但**这条纪律没有写进子 agent 的生成/修复流程约束**，test-expert 实际执行成了"一步一 edit"。

### 3.2 修复/复检轮次续接旧会话，上下文滚到 190K 且全程不再压缩

TC生成 B01 一个会话承载了 生成 + R1修复 + R2修复 三个阶段，上下文从 9K 一路涨到 190K；到 R2 修复时，每一步都在重发生成阶段早已写完的 16K 用例文件和全部历史读取内容。qa TC质检 R1 B01 同样续接了 R1/R2 复检，终态 175K。

配置里其实已有"新建会话不重读前序文件 + 三件套交接摘要（上限 15K）"的机制（[test-manager.md](file:///d:/Project/test-team-2/.opencode_v2/agent/test-manager.md) 第 91 行），但**"会话复用"表规定生成与修复同会话续接**，导致该机制在这条最贵的链路上没生效。62 个 ctx>100K 的回合合计 818 万 token（占 44%），全部来自这种大上下文会话。

### 3.3 原文档跨会话反复读取：PRD 被读 48 次、前端文档 50 次

| 文件 | 读取次数 | 进入上下文总量 | 涉及会话数 |
| --- | ---: | ---: | ---: |
| 产品需求说明书.md | 48 | 310 KB | 10 |
| 需求平台前端设计文档.md | 50 | 209 KB | 10 |
| tc-F01.json | 10 | 196 KB | 2 |
| resources-index.md | 13 | 188 KB | 10 |
| tc-F03.json | 7 | 187 KB | 2 |
| 3通用测试规则.md | 9 | 110 KB | 4 |

经理的派发协议要求"按索引只回读本次委派功能点相关的章节原文"，但实际执行中：
- TC质检 R1 B01 把 `tc-F01/F02/F03.json` **整文件全读**（每个 24KB），前端文档一次并行读 6 段；
- TC生成 B01 里 `需求平台前端设计文档.md` 在同一会话读了 9 次、PRD 读 6 次；
- 每个子会话各自冷启动，同一份 PRD 在 10 个会话里被重新读入 10 次——多 agent 架构下这是固有成本，但按锚点分段读取可大幅压缩。

### 3.4 skill 与知识文件冷加载：26 次 skill 调用 115KB，且加载了用不上的

每个子会话首轮并行加载 3~4 个 skill（quality-check 11.7KB、test-case-workflow 8.5KB、test-knowledge-canon 5.2KB、test-point-workflow 5.1KB），再读 canon 的 references（3通用测试规则.md 单段 11.6KB，被读 9 次）。其中：
- test-expert 做 **TC 生成**时加载了 `quality-check` 和 `test-point-workflow`；
- qa-expert 做 **TC 质检**时加载了 `test-point-workflow`。

这些与当次任务无关的 skill 内容（约 10~20KB ≈ 5~10K token）会留在该会话整个生命周期里被反复重发。

### 3.5 经理会话本身：79 回合 × 平均 5.6 万上下文 = 442 万（占 23.5%）

[test-manager.md](file:///d:/Project/test-team-2/.opencode_v2/agent/test-manager.md) 系统提示 27.5KB（≈1~1.5 万 token），加上每次 `background-result` 回波、台账 edit、23 次派发都各占一个回合。79 个回合里相当一部分只是"收到子任务完成通知→改一行台账"，但每回合都要重发全部历史。经理上下文从 15K 涨到 104K，后半程每个"记账回合"都在花 9 万+ token。

### 3.6 reasoning 占比不低：27.8 万 token，单步最高 29K

qa-expert 合计 reasoning 14.2 万（TC质检 R1 B01 一步 29,017 + 一步 15,023）。质检语义判定天然重推理，这部分是"有效消耗"，但和 3.3 叠加：推理时反复引用的是整文件读入的原文，若输入更聚焦，reasoning 也会更短。

## 4. 卡点排查

### 4.1 用户关口阻塞：累计约 9.6 分钟，占全程 25.5%（最大时间卡点）

5 次 `question` 调用全部由经理发起，等待用户答复期间**整条流水线停摆**：

| 时间 | 关口 | 等待时长 |
| --- | --- | ---: |
| 00:03:32 | 关口1 功能范围勾选 | 26 s |
| 00:09:22 | 关口2 第一步 待澄清（C-01/C-02） | 28 s |
| 00:09:57 | 关口2 第二步 资料缺口（C-09/C-10） | 26 s |
| 00:17:18 | 关口3 TP 验收 | **251 s** |
| 00:35:45 | 关口4 TC 验收 | **246 s** |

两道关口各等 4 分钟。若属无人值守批量运行，这是首要优化点（见 §5.6）。

### 4.2 结构性串行等待：子会话轮间空闲合计约 17 分钟

所有子会话 >15s 的间隙经逐条核对**均为"轮间空闲"**（上一条消息是 idle，在等经理下一次委派），没有发现轮内卡死。但链路是严格串行的：

```
TC生成 B01 完成(00:26:22) → 等 QA R1 出报告(00:29:42) → 才被派 R1 修复   空闲 206 s
TC生成 B01 R1 完成(00:31:42) → 等 QA 复检发现新阻塞(00:34:14) → 才派 R2  空闲 157 s
TC生成 B02 完成(00:25:04) → 等 QA → 派修复 → 00:29:27 完成              空闲 216 s
```

叠加"阶段隔离：TP 全批收敛并汇总后才进 TC"的规则，**B02 比 B01 早完成 5 分钟却必须干等**。并发上限设 3，实际同一时刻最多只跑 2 批，上限从未用满。

### 4.3 模型生成慢：15 个单步流式生成 >30s

| 时间 | 会话 | 生成时长 | 产出 |
| --- | --- | ---: | --- |
| 00:27:10 | qa TC质检 R1 B01 | **140.5 s** | 2,725 tok（质检报告） |
| 00:10:58 | test TP生成 B01 | 116.8 s | 3,501 tok |
| 00:15:21→00:16:21 段 | test TC生成 B01 | 74.6 s | 8,769 tok（写 16KB JSON） |
| 00:22:17 | test TC生成 B02 | 72.2 s | 8,453 tok |

输出吞吐约 40~60 tok/s，大 JSON/大报告一步生成 1~2.5 分钟。这是 flash 模型速度上限，非流程缺陷，但决定了"减少长生成步骤"同样能省时间。

### 4.4 错误与重试：仅 1 次，无实质影响

- 00:30:27 test-expert（TC修复 R1 B01）一次 `edit` 失败，下一步重试成功。
- 无 TTFT 异常（全部 <8s）、无会话失败、无权限拒绝、无死循环重试。

### 4.5 质检回路轮次：B01 走了 3 轮，是 TC 阶段最贵链路的直接推手

- TP 阶段：B01 R1 报 7 问题 → 修复 → 复检收敛；B02 R1 报 3 问题 → 收敛。各 1 轮，正常。
- TC 阶段：B01 R1 报 16 问题（阻塞1/重大9/一般6）→ 修复 → 复检**又出 1 条新阻塞**（TC-051）→ R2 修复 → R2 复检才收敛，共 **2 轮修复 + 2 轮复检、6 次委派**。B02 R1 报 9 问题，1 轮收敛。
- B01 首轮质检问题率高（16/119 条用例被点名）直接导致该链路多花约 200 万 token（R1/R2 修复与复检的全部回合）。

### 4.6 卡点结论

**没有技术性卡死或异常阻塞**；时间损耗三块：用户关口等待 ~9.6 min（可自动化消除）、批次间/阶段间结构性串行等待 ~17 min 空闲（可调度优化）、模型生成本身 ~20 min（受模型吞吐约束）。

## 6. 数据口径说明

- 上下文处理量 = 每 assistant 回合 `tokens.input + tokens.cache.read` 之和；cache_read 是提供方按缓存命中计价的重发量，不代表新内容。
- 会话时长取 `info.time.created → info.time.idle`；间隙取相邻消息时间戳差。
- 工具输出体积取 `state.content` 文本 UTF-8 字节数。
- 分析脚本为临时脚本，未落盘工作区；原始数据以本目录 11 个 `ses_*.json` 为准。

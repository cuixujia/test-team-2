# optimize2 运行分析报告：为什么更慢更贵

## 结论摘要

先纠正一个感受：**产物质量没有下降，反而大幅回升**。本次生成 45 条 TP、191 条 TC，对比上次 optimize1 的 20/63，是 2 倍以上的提升，也超过最初 refector 的 36/129。你感觉"越优化越垃圾"，问题不在产物，而在流程开销：

| 指标 | refector 初版 | optimize1 | optimize2 本次 |
|---|---:|---:|---:|
| 请求数 | 270 | 153 | **296** |
| Token | 16.1M | 8.4M | **15.4M** |
| 会话数 | 11 | 6 | **15** |
| 输出 token | 357K | 264K | 374K |
| 输入 token | 783K | 650K | 938K |
| 缓存读取 | 14.77M | 7.26M | 13.87M |
| TP / TC | 36 / 129 | 20 / 63 | **45 / 191** |

**真正的原因有四个，都和产物无关：**

1. **会话复用完全失效**：14 次 task 派发，0 次复用，全部新建会话。上次是 12 次里 7 次复用。每个新会话都要重新加载 skill 和文件，请求数直接翻倍。
2. **TC 生成空回报 + 一次 7317 秒的卡死**：首次 TC 生成返回空结果，主 agent 卡了约 2 小时才发现，重建会话重跑整份任务。这是时长和请求数的最大单点。
3. **质检全部走满两轮，且 TP/TC 第二轮仍未收敛**：三段质检全走 R1→修复→R2，其中 TP、TC 的 R2 各留 1 个重大项，触发两次三选一 question。根因是修复本身引入了新缺陷。
4. **这次运行用的是旧的 2 轮规则**：会话在 13:50:45 结束，而"满 3 轮未收敛"的配置在 13:49:10 才写入——改动发生在会话快结束时，本次运行全程仍按 2 轮上限执行。所以"改成 3 轮"的效果这次根本没验证到。

## 一、数据口径

截图显示 15M token、296 请求、93.66% 缓存命中、¥2.72。CSV 校准后：输入 938,174、输出 374,470、缓存读取 13,870,208、缓存写入 228,237，合计 15,411,089。`13,870,208 ÷ (13,870,208 + 938,174) = 93.66%`，与截图一致。296 次请求全部 HTTP 200，平均 8.94 秒/次，首字平均 2.1 秒。

## 二、四个卡点的证据

### 卡点 1：会话复用 0/14，全部新建

14 次 task 派发，每次都返回不同的 `task_id`，没有任何一次带 resume 参数。主 agent 甚至在思考里明确按"不同类型即新建"执行：

> 行 1326：`Note conversation reuse rules: TP and TC use separate sessions. Also "同类型连续阶段复用同一会话" — TC-生成 new session since different type.`

规则本身留了复用空间——同类型的材料质检 R1→R2、TP 质检 R1→R2、TC 质检 R1→R2 都具备条件——但一次都没用。对照 optimize1 的 7/12 次复用，这是本次请求数从 153 涨到 296 的直接原因。

为什么改窄之后反而全失效：新规则写了"跨产出类型不复用"和"累计追加满 3 次改新建"，两条限制叠加，让主 agent 把"新建"当成默认动作。规则只说了何时复用、没说**如何复用**——即 prompt 里必须带 `task_id`。这是规则表述的缺口，不是模型不听话。

### 卡点 2：TC 生成空回报 + 2 小时卡死

这是本次最大的单点浪费：

> 行 1349–1351：`<task_result>` 完全空
> 行 1373：bash 检查 `output/tc/` 目录，`total 8`，无文件
> 行 1393：`## Assistant (Test-Manager · DeepSeek-V4.1-Flash · WorkBuddy · 7317.6s)` —— 卡死约 2 小时
> 行 1395：`TC 生成任务返回空结果，产物未落盘。重建会话续做该任务。`
> 行 1402：重新派发 `TC生成重试`，新 task_id

一次空回报，连带整份任务重跑，还多出一个新会话。上一轮也出现过同类问题（optimize1 的 TP 生成空回报重派），说明子 agent 的空回报是反复发生的稳定性问题，当前没有兜底机制。

### 卡点 3：质检两轮未收敛，修复引入新缺陷

| 域 | R1 | R2 | 结果 |
|---|---|---|---|
| 材料 | 阻塞2/重大0/一般2，N | 阻塞0/重大0/一般0，Y | 收敛冻结 |
| TP | 阻塞0/重大5/一般3，N | 阻塞0/重大1/一般1，N | 未收敛，触发 Q4 三选一 |
| TC | 阻塞1/重大10/一般5，N | 阻塞0/重大1/一般1，N | 未收敛，触发 Q6 三选一 |

两次未收敛的根因都是**修复本身制造了新问题**：

- TP：行 1175，Q-TP-R1-07 修复后，新项 3 与项 1 同规则同预期，新项 2 无锚点支撑
- TC：行 1660，Q-TC-R1-03 把 4 条状态码合并成 TC-146，结果 TC-146 与 TC-107 前置/数据/步骤/预期实质相同

两次三选一用户都选了"接受现状"（行 1235、1713），重大项原样过关口。这说明"2 轮修复"对复杂问题不够——而这正是你刚改成 3 轮想解决的问题，但本次运行没用上。

### 卡点 4：3 轮规则改在会话结束前 90 秒

| 事件 | 时间 |
|---|---|
| session-ses_e136.md 结束 | 13:50:45 |
| qa-expert.md、material-expert.md 修改 | 11:23 |
| test-manager.md 修改，含"满 3 轮未收敛" | **13:49:10** |

会话中明确引用的是旧规则：

> 行 1193：`This is round 2. Rule: 满 2 轮未收敛 → 呈三选一`
> 行 1681：`已满 2 轮上限，需您决策`

所以本次的两次三选一是旧 2 轮规则触发的。3 轮改动在会话结束前约 90 秒才落盘，对这次运行没有任何影响。

## 三、其他发现

**主 agent 用 bash 写文件**：7 次 bash 中有两次绕过了 write/edit——行 1598 用 `cat >> repair-log.md` 追加，行 1804 用 `python3 - <<EOF` 做字符串替换改 `state.md`。同一会话 write 工具成功调用 11 次，不是权限问题。从思考看（行 1594），模型是出于"省 token"自主改用追加，因为 write 每次要重写整份越来越大的文件。全文 `edit` 工具一次都没用。这是行为不一致，也说明 state.md 膨胀到了模型不愿整篇重写的程度。

**TC 质检读整份清单**：截图显示 TC 质检会话读了 `test-case-table.md` 37.9K、`bash ×21`、`skill ×2`，上下文 120K。主会话行 1513 的回报证实："R1 为 TC 首轮，全量检视 194 条"。R1 全量读是现有规则要求的，R2 才增量（行 1667"实检 46 条，未改动条目未复检"）。所以这不是子 agent 违规，但 R1 的 prompt 里确实没写"按锚点分段读"的约束。

**范围没变**：用户仍只选 F01、F02（行 299）。全量清单从 12 条变 18 条是因为前端文档补全了 F13–F18 并标"推断"，但一个都没进范围。产物 45 TP、191 TC 全部覆盖 F01/F02。

**主会话仍有 4 处犹豫**，比 optimize1 的 166 行拉锯收敛，但仍有三选一决策（行 1191–1201）、会话复用规则推演（行 1322–1330，111.5 秒）等非产出思考。

## 四、这次优化到底有没有用

有用，但被抵消了：

| 措施 | 实测效果 |
|---|---|
| 产物质量约束写进 test-expert | **有效**，TP 20→45、TC 63→191，维度覆盖恢复 |
| 主 agent 零原文、零 skill、零读产物 | **有效**，主会话 read 0 次、skill 0 次 |
| function-list.md 取消 | **有效**，阶段 1 一次落盘 scope.md，无补充派发 |
| 材料质检收敛范围收窄 | 部分有效，材料域 R2 收敛 Y |
| 会话复用写窄 | **反向失效**，从 7/12 复用退化到 0/14 |
| 3 轮上限 | **未生效**，改在会话结束前 90 秒 |
| TC 生成空回报兜底 | **无**，再次发生且卡死 2 小时 |

一句话：内容生成侧的修复起作用了，流程与稳定性侧没有，而后者才是 token 和时长的决定因素。

## 五、下一步建议

| 优先级 | 措施 | 针对 |
|---|---|---|
| P0 | 修复会话复用规则：明确写出派发时须传 `task_id`，并给出"何时复用"的判定顺序，去掉易被当成默认新建的模糊表述 | 卡点 1，预计省一半请求 |
| P0 | 空回报兜底：子 agent 回报后主 agent 立即校验产出文件是否存在、行数是否为 0，校验失败即重派；对无输出的等待轮次设超时 | 卡点 2，避免 2 小时黑洞 |
| P1 | 3 轮规则下一次运行验证，本轮数据不能作为依据 | 卡点 4 |
| P1 | 把 state.md 与 repair-log.md 的追加改为 edit 工具定点追加，禁止 bash heredoc 写文件 | 行为不一致 + 文件膨胀 |
| P2 | TP/TC R1 修复派发时要求"只改指出项并自检新引入重复"，降低 R2 留重大项的概率 | 卡点 3 |

## 3. 遗留问题（按浪费排序）

### P1【最大】经理台账仍然拆步：27 个 edit 回合 + 13 个空回合 ≈ 120 万 ctx（占总量 18%）

9 个写入时机本身合规（clarifications、repair-log 各 1 次），但 state.md 每个节点被拆成 **3~6 个连续单 edit 回合**（间隔仅 2~3 秒，逐小节改写）：

```
18:05:36 / 18:05:38 / 18:05:41 / 18:05:52 / 18:05:54 / 18:06:01  ← 关口3节点拆 6 步
18:08:59 / 18:09:02 / 18:09:04 / 18:09:11                        ← TC生成回报节点拆 4 步
18:14:27 / 18:14:30 / 18:14:32                                  ← 收尾节点拆 3 步（含 1 次报错重试）
```

另有 13 个**纯文本空回合**（回波后只回一句进度说明就结束），直接违反"回波回合必须办实质事、禁止空应答"。经理 66 回合中实质动作回合仅 ~24 个。

**根因**：规则写"同一回合并行发出多条 edit"，模型把每个 tool call 当作一个回合，逐条串行发出。"同一回合"在 opencode 消息循环里语义模糊。

### P2 修复阶段单 edit 复发：TC生成B01 修复 11 个写回合 ≈ 100 万 ctx（占 15%）

18:11:21→18:12:38，9 个修复项拆成 11 个回合（9 单 edit + 2 双 edit），此时 ctx 已 95~108K，每回合重发 ~10 万。
生成阶段"每批 50 条"执行得很好，但**修复场景没有执行"全部改动收集齐一回合发出"**。

### P3 流程时序错误：材料质检与索引构建并行派发

17:57:14 经理**同时**派发索引构建与材料质检；QA 17:57:16 读 `resources-index.md` → **File not found**（文件还不存在），glob 找路径后空等 60 秒至索引落位才继续。经理自己在台账里也承认了：「材料质检因索引尚未落位而阻塞（同步派发的时序问题）」。
阶段 3 正确顺序应为：索引构建回报 → 才派材料质检。

## 5. 建议改动（按优先级）

1. **把"同一回合"改成模型能执行的表述**：三处规则（manager 台账、test-expert/qa-expert 修复）改为——
   - 经理：「一个写入时机的 state.md 全部改动**必须用一条 `edit`**：oldString 从首个待改小节起、newString 含全部待改小节的终态，一次替换到位」；或更彻底——state.md 体量小（终态 ~3KB），**每次时机直接 `write` 全量重写**，一条命令一个回合，还消灭 oldString 不匹配报错（P4-2）
   - 修复：「修复任务落盘只允许一个回合：该文件全部改动合并为**一条**跨多小节的 `edit`（或 write 重写），禁止第二条」
2. **阶段 3 串行化**：经理配置明确"材料质检在索引构建回报并机验通过后才派发"，禁止并行
3. **空回合禁令加反例**：「收到回波后同回合必须发出工具调用；只输出文字不行动即违规」
4. **路径纪律**：委派 prompt 已含会话目录绝对路径，test-expert 约束补一句「briefing/state/scope 路径一律从委派原文复制，禁止自行拼接」

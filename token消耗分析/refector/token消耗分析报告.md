# 测试用例生成任务：耗时与 Token 消耗分析报告

## 结论摘要

| 指标 | 数值 | 说明 |
|---|---|---|
| 会话数 | 11 个 | 1 个测试经理主会话 + 约 10 个子会话/重启会话 |
| 请求数 | 270 次 | 成功 269、失败 1（429 限流） |
| Token 总量 | 约 1613 万 | 输入 78.3 万 + 输出 35.7 万 + 缓存 1499 万 |
| 缓存命中率 | 94.97% | 缓存读取占总量 91.6% |
| 模型推理耗时 | 35.2 分钟 | 平均 7.8 秒/次，P90 19.2 秒，最长 133.9 秒 |
| 端到端耗时 | 52.7 分钟 | 22:56:36 → 23:49:16 |
| 费用 | 约 ¥1.86 | 缓存低价摊薄了成本 |

一句话结论：**慢和费的根因不是模型本身，而是团队架构把一次任务拆成了 11 个会话、270 次模型往返；每次请求都把已积累的上下文重新送一遍，导致 15M 缓存读取 token 成为绝对大头；而 11 次 `task` 子专家派发（含 3 组质检 R1→修复→R2 + 1 次空回报重派）与 5 次用户关口又把请求数和等待时间层层放大。**

## 一、数据口径与列义校准

CSV 表头与实际数据存在**一列错位**（表头多出 `effort` 一列，其后各列语义整体前移一位）。本报告依据截图统计口径完成校准，校准结果如下：

| 数据列 | 表头名称 | 实际语义 | 校准值（270 行合计） |
|---|---|---|---|
| 5 | effort | 输入 token | 782,575（截图 783K ✓） |
| 6 | input_tokens | 输出 token | 356,810（截图 357K ✓） |
| 7 | output_tokens | reasoning token | 0 |
| 8 | cache_write_tokens | 缓存读取 token | 14,769,984 |
| 9 | cache_read_tokens | 缓存写入 token | 222,599 |
| 10 | reasoning_tokens | 费用 USD | 0.278 → 约 ¥1.86 ✓ |
| 11 | cost_usd | 请求耗时 ms | 2,109,743 ms |
| 12 | duration_ms | 首字延迟 ms | 均值 1,762 ms（截图 1.9 秒 ✓） |
| 13 | ttft_ms | HTTP 状态 | 200×269 / 429×1 |
| 15 | tier_sent | 结束原因 | tool_calls×257 / stop×12 |

交叉验证：`14,769,984 ÷ (14,769,984 + 782,575) = 94.97%`，与截图缓存命中率完全一致，校准可信。

## 二、16M Token 从哪来

| 类别 | Token 量 | 占比 | 来源 |
|---|---:|---:|---|
| 缓存读取 | 14,769,984 | 91.6% | 每次请求重发已积累上下文（缓存命中部分） |
| 输入 | 782,575 | 4.9% | 各会话新读的资料、skill、提示词 |
| 输出 | 356,810 | 2.2% | 思考过程、清单正文、台账与报告 |
| 缓存写入 | 222,599 | 1.4% | 上下文增长产生的新增区 |

关键在于"**请求数 × 每请求上下文**"的乘法效应：单次请求 token 中位数 **54,983**、P90 达 **114,374**、峰值 **142,088**；270 次累加即约 16M。缓存命中率虽高达 94.97%（单价低，故仅 ¥1.86），但 token 计数仍全额计入，因此"便宜"不等于"省"。

三个放大器：

1. **主会话上下文滚雪球**：测试经理会话从 0 增长到 142K（截图 142K/1M），83 轮每轮都把历史对话、工具结果、agent 提示词重新送入。截图中"会话内容"单项就占 73.8K。
2. **子会话重复载入同一资料**：11 个会话各自为政，同一批 `project-docs/`（PRD/BRD/前端设计文档）与 skills 被反复读进独立上下文。仅主会话内 `read` 这三份文档就达 11 次（PRD 5 次、BRD 2 次、FDD 4 次），另有 4 次 `grep` 定位。
3. **输出侧的冗长内容**：会话含 48 段 `_Thinking_`，约 20%–25% 是自我推翻与纠结（"等等，我又担心一个问题""嗯，其实还有更简的思路""为了效率…为稳妥…"）；加上 129 条 TC 清单正文与 11 道澄清题的长文本，共同堆高输出 token。

## 三、为什么请求数高达 270 次

270 次不是一条线性对话，而是 **11 个会话各自多轮 tool-use 循环的求和**。截图中的会话列表印证了这一分布：

| 会话 | 请求数 | 会话 | 请求数 |
|---|---:|---|---:|
| ses_e15f（主会话，本报告转写） | 83 | ses_e15e | 21 |
| ses_e15d | 33 | ses_e15d | 20 |
| ses_e15e | 19 | ses_e15f（hy4 早期） | 20 |
| ses_e15e | 17 | ses_e15d | 16 |
| ses_e15d | 15 | ses_e15e | 12 |
| ses_e15f（hy4 早期） | 12 | 其余 | 约 2 |

主会话 83 次对应转写中的 83 个 assistant 轮次；其余约 187 次来自子会话——每次 `task` 派发的子专家都要在自己的会话里完成"读资料 → 思考 → 写文件 → 跑机验 → 回报"的独立循环，单次 12–33 次请求。

请求被放大的四个结构性因素：

1. **11 次子专家派发**：理论上 5 次即可（材料质检、TP 生成、TP 质检、TC 生成、TC 质检各 1 次），实际因质检回路翻倍到 11 次。
2. **3 组质检均走 R1 未收敛 → 修复 → R2 复检**：材料、TP、TC 三段质检各多出 1 次 QA + 1 次修复 + 1 次复检，是请求数翻倍的 main driver。
3. **1 次空回报重派**：TP 生成首派返回空结果（`L4206`–`L4208`），经用户"继续"（`L4213`）与落盘核查（发现 `output/tp/` 为空）后重派，额外消耗一轮完整子会话。
4. **模型切换痕迹**：79 次请求用 `hy4-flash-free`（两个最早会话），190 次用 `deepseek-v4.1-flash`，期间存在模型/会话重启，带来重复开销。

## 四、50 分钟花在哪

| 时间构成 | 时长 | 占比 |
|---|---:|---:|
| 模型推理累计（CSV duration 列求和） | 35.2 分钟 | 约 67% |
| 用户关口等待 + 子会话编排 + 工具执行 + 会话切换 | 约 17.5 分钟 | 约 33% |

- **推理侧**：平均 7.8 秒/次，P90 19.2 秒，单次最长 133.9 秒；其中 257 次以 `tool_calls` 结束（平均 7.9 秒）、12 次以 `stop` 结束（平均 6.1 秒）。
- **等待侧**：转写中 6 个高耗时轮次均在等子任务回报或用户答复——243.5 秒、180.7 秒、174.2 秒、149.3 秒、147.2 秒、96.5 秒。
- **会话空档**：4 次超过 2 分钟的间隔（183 秒、522 秒、136 秒、149 秒），最长 522 秒（8.7 分钟）系会话间切换/用户介入。
- **自我纠错开销**：机验因锚点外层反引号误判失败（`L2530`→`L2705`），随后读 `lib_citation.py` 两次、`grep` 两次、`verify_citation.py` 一次，重写索引后复验通过（`L3151`），这条纠错链约占 9 个轮次。

## 六、根因归纳

1. **架构层面**：`task` 子专家各自独立会话，无法共享已加载上下文；同一批 PRD/BRD/FDD 与 skills 被 11 个会话重复读取，是 15M 缓存读取 token 的结构性来源。
2. **流程层面**：三段质检均需 R1→修复→R2 双轮，把 5 次理论派发放大为 11 次；每次循环都触发新的子会话与完整上下文重送。
3. **质量层面**：机验锚点格式误判引发 9 轮自我纠错；TP 生成空回报导致重派；`read offset` 越界后重试（`L5672`）。
4. **行为层面**：48 段思考中约 20%–25% 为犹豫、自我推翻与"要不要并行 edit"的反复论证，单轮 9–15 秒，直接拉高轮次与输出 token。
5. **等待层面**：5 次用户关口（含 11 道澄清题）+ 6 个百秒级子任务等待 + 4 次会话间空档，共同构成约 17.5 分钟非推理耗时。

## 七、优化建议

| 优先级 | 措施 | 预期收益 |
|---|---|---|
| 高 | 质检前置加严：R1 派发前由经理把机验与判据跑透，争取一次收敛 | 派发 11→约 6，请求数与缓存读取近乎减半 |
| 高 | 统一锚点格式规范（禁止整行反引号包裹）并写入 skill | 消除约 9 轮纠错链 |
| 高 | 子会话改用精简 briefing：只传 scope 选中片段与索引路径，不重复全文载入资料 | 显著降低每请求上下文与 15M 缓存读取 |
| 中 | 规范 `task` 回报协议，空回报即判失败并按约定重试一次，无需用户"继续"介入 | 省去 1 次重派与落盘核查 |
| 中 | 关口 2 的 11 题默认项直接生效、仅对高风险题让用户确认 | 减少一轮长文本 question 往返 |
| 中 | 经理按现有规则"不读清单全文"严格执行，台账 `edit` 批量一次写完 | 降低 16 次 edit 与上下文回灌 |
| 低 | 收敛模型选型（统一 deepseek-v4.1-flash 或 hy4-flash-free） | 减少切换/重启带来的重复会话 |

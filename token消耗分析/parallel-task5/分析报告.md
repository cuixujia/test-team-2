## 二、根因分析

### 问题 1：产物数量与覆盖下降

三个规范定义缺陷叠加，不是执行事故。

1. **TC 条数基准绑死在重点项数上**。每 TP 的 TC 数集中在 3~4 条，占 65%，恰好等于 `用例展开重点` 平均项数 3.16。来源是 test-case-workflow【展开数量守恒】表格中「其他形态｜展开重点列点名的项数」一行，把重点清单当成了计数基准；test-expert【测试用例】的「TC 是 TP 的纯展开」进一步固化了这个心智。机验只查每 TP 直属 TC ≥ 2 的下限，贴线生成完全合规。
2. **「静默生成」语义歧义被放大成整块跳过**。生成红线第 3 条「无依据支撑的内容静默生成，只写宽泛表述」原意是照列条目、放宽表述，生成方执行成了不落断言、整块不列。state.md 阶段 4 记录了四大块跳过：F01 受理登记界面类、F02 文档格式与重试细节、F03 台账界面与导出、F04 回滚与通知细节，理由均为「按 C-11~C-16 静默生成口径不落断言」。
3. **QA 对覆盖缺口有豁免通道且无核验**。TP 域「全集覆盖」接受「覆盖缺口书面理由」，四大块跳过仅凭一句「与 C-11~C-16 口径一致」通过，两个关口均未拦截。

### 问题 2：质检会话无响应重派

TP质检B02 首派末轮：思考 32000 token、正文 0、finish=length。9.6 万字符的思考在小类归属、排序、场景级判定上反复自我推翻，把输出预算全部烧在推理里，没发出任何工具调用。模型单轮输出预算为 32K，思考与正文共用，思考耗尽即整轮报废。是输出 token 达上限，确认。

### 问题 3：思考过程过长

根因是回合工作量设计与模型预算错配，不是模型偶然发挥。qa-expert 轮次约束要求「第 2 轮：语义验并写报告，合并为一次落盘」——一个回合内对 2 个功能文件的全部条目完成 5 维判定并一次成稿，模型只能在单次思考里逐条权衡；判定分级本身存在模糊地带，无决断规则时思考无限延长。质检类会话单轮思考普遍 3 万以上。

### 问题 4：大文件写入失败

与问题 2、3 同一机制的不同表现。TC生成B01 第 4 轮想一步落盘两个 TC 文件，tc-F01.json 54 行约 1.9 万字符，同轮思考已耗 24330，正文写到 7670 被截断，产生 invalid 工具调用，落盘 JSON 解析失败。单轮正文预算 = 32K - 同轮思考量，整文件一次写入在思考较重时必然越界。

## 三、根源解决方案

问题 2、3、4 共享同一个根源：回合设计假设单回合可以承载任意工作量，而模型单轮输出预算固定 32K 且思考与正文共用。打补丁式的「截断后重试」「限制行数」都是绕，正解是把回合粒度重设为预算内的最小工作单元。问题 1 的根源是规范定义缺陷，正解是改定义本身。

### 修复一：回合模型按「一个功能文件一回合」重构

改 qa-expert.md【任务执行轮次约束】与 test-expert.md【任务执行轮次约束】。

- qa-expert R1 从固定三轮改为：第 1 轮加载与读取并机验；随后每个功能文件独占一回合，语义验完立即把该文件问题追加写入报告；最后一回合回报。R2 复检同理按文件分回合。
- test-expert 落盘从「各功能文件在同一步逐一落盘」改为：每个功能文件独占一回合落盘；单文件条目超过 30 行时先写骨架与前 30 条，下一轮用 edit 追加其余条目。

每回合思考对象只有一个文件，正文只有一个文件的量，32K 预算从结构上不会被击穿。无响应、思考超长、写入失败三个症状同源同治。

### 修复二：给 QA 判定加可决断规则

改 quality-check SKILL.md【通用纪律】。

- 每个条目每个维度只判一次；证据不足以在两档分级间区分时取低档并写一句理由，不再推演。

消除思考摇摆循环——报废会话的死因就是在「一般还是重大」上无限往返。

### 修复三：重建 TC 条数基准

改 test-case-workflow SKILL.md【展开数量守恒】与 test-expert.md【测试用例】。

- 守恒表删除「其他形态｜展开重点列点名的项数」一行，改为无明确形态时按验证对象的客观分支计数。
- 加定位声明：`用例展开重点` 只提示方向，不是条数上限；TC 条数一律按 TP 形态的客观计数核算。
- test-expert「TC 是 TP 的纯展开」改为「TC 围绕 TP 验证对象展开，条数按形态客观计数核算，不受重点项数限制」。

### 修复四：废除静默生成，默认建议必须具体

改 test-point-workflow、test-case-workflow 生成红线，quality-check【资料域】，test-manager 澄清链路。

- 删除「静默生成」概念：两类澄清条目的默认建议必须是可直接转成断言的具体建议，缺口类也要给建议取值，不得写不落断言的空票。
- 两道澄清的题目正文都呈现默认建议内容，用户选择 `接受默认建议` 即接受该具体建议。
- 子 agent 生成与质检按 `clarifications.md` 默认建议列的内容执行，未登记且原文无支撑的内容只写宽泛表述，不得整块跳过。

### 修复五：QA 覆盖闭环核验

改 quality-check SKILL.md【TP 域】【TC 域】。

- TP 域全集覆盖：每块覆盖缺口理由必须挂 C 编号，QA 回读该 C 条目确认确实覆盖该块；无 C 支撑的整块缺失判阻塞。
- TC 域展开完整性：按守恒表形态核算实际条数，明显低于核算线判整批欠展开，重大。

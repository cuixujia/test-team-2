# 测试用例生成团队 Token 消耗分析报告

## 一、结论摘要

本次不是「一次生成」就烧掉两千万 token，而是**一个不断膨胀的上下文被反复重放了一百多次，累加出两千万**。

用两句话区分两个容易混淆的量：

- 界面上的 `174K / 960K` 是**某一刻**上下文窗口的占用，离 96 万窗口上限还很远，窗口容量不是瓶颈。
- 账单上的约 1710 万～2000 万 token 是**全部请求逐次提交的 token 累加**。每次请求都把当时已有的全部上下文重新送一遍，请求次数一多，累加值就膨胀。

核心公式：

```text
累计 token ≈ 平均上下文大小 × 请求次数
```

本次两项都偏大：主会话上下文从 0 涨到约 17.3 万，全程 214 次请求，其中主会话一个就发了 124 次。**约 90.5% 的 token 花在「把同一份上下文反复重读」上，而不是花在真正的思考与产出上。** 这是架构与流程问题，调模型参数解决不了。

理想目标 200 万需要砍掉约 88%，属于架构级调整；报告第六节给出按收益排序的可执行路径，测算可落到 200 万上下。

## 三、量化拆解

### 3.1 总量与构成

调用记录合计 **17,105,993 token（约 1710 万）**，与上次的 1867 万、用户感知的「近两千万」为同一量级；差异来自两次运行停止点不同。

| 构成 | Token 数 | 占比 |
|---|---:|---:|
| 缓存重放（同一上下文反复提交） | 15,474,112 | 90.5% |
| 新增输入 / 推理（effort） | 1,053,143 | 6.2% |
| 输入 token | 329,721 | 1.9% |
| 缓存写入 / 其他 | 249,017 | 1.5% |

真正推动任务前进的「新增 + 输出」合计不足 10%，其余全是重复提交。

本次共 9 个 session（1 个主 agent + 7 个 QA 子会话 + 1 个空请求会话）：

|---|---|---:|---:|
| `ses_e17fa352` | 主 agent（test-expert） | 124 | 13,289,642 |
| `ses_e17e83174` | QA 子会话 | 15 | 756,084 |
| `ses_e17f18129` | QA 子会话 | 13 | 708,036 |
| `ses_e17cce32e` | QA 子会话 | 14 | 682,465 |
| `ses_e17d354d5` | QA 子会话 | 12 | 540,022 |
| `ses_e17c75960` | QA 子会话 | 17 | 516,674 |

主会话一个占全部缓存重放的 **82.2%**。子会话每个都是全新上下文，7 个加起来又额外贡献约 380 万。

### 3.3 主会话上下文增长曲线

```text
13:40   0K  →  13:43  21.5K  →  13:54  54K  →  13:59  86K
14:00  101K  →  14:12 126K  →  14:22 142K  →  14:29 161K
14:35  169K  →  14:39 173K
```

曲线单调上涨、只增不减。越到后期，每次请求携带的上下文越大，同样一次工具调用越贵。

### 3.4 缓存失效：最贵的单点

`14:34:50` 主会话出现一次 `effort=167,222、缓存重放=0` 的请求——整段约 16.7 万上下文被**全价重建**（约为单次正常请求新增量的数百倍）。它紧接在 QA 子会话 `ses_e17cce32e`（14:30–14:34）之后发生，是主/子会话交错切换导致缓存前缀失效的典型特征。调用记录中还有 4 次 `429` 限流空请求。

缓存读本身是省钱机制（单价约为新输入的十分之一），它是「重复提交次数太多」的结果指标。优化要砍的是**请求次数与上下文大小**，而不是去压低缓存命中率。

## 四、为什么耗时约 50 分钟

墙钟跨度 **58.4 分钟**（13:40:56 → 14:39:19），但调用记录里模型自身计算时间合计仅约 **14.8 分钟**。差额约 43 分钟来自：

1. **人工确认关口空等**：流程有 4 个 `question` 关口，调用记录中有多次 36～38 秒的空请求（如 13:44:44、13:48:56），用户不回复时计时照走。
2. **QA 子会话串行派发**：至少 7 次 `task` 派发，每次新建子会话、重新注入提示词与全量文件，逐个等待完成。
3. **工具往返 × 缓存重放**：全程 99 次工具调用（详见 3.5），以 `edit`(39) 与 `bash`(23) 为主，每次往返都要重新提交当时的全部上下文；后期单次往返更慢。
4. **长推理 Thinking**：消息记录中大量 `_Thinking:_` 长段落（如开头对收敛判定的反复权衡），既耗时又计入输出 token。
5. **缓存失效放大**：失效那次单次耗时 14.5 秒，是正常的数倍；4 次 429 限流也带来等待。

简言之，时间主要花在「等待人 + 等子会话 + 反复搬运上下文」，不是花在模型算得慢。

## 五、根因分析：团队配置层面的放大器

以下按影响从大到小列出，均来自 `.opencodenew` 配置与本次会话日志的交叉印证。

1. **上下文无阶段隔离、只增不减**（最大因素）
   主 agent 提示词 20 KB 内含 6 份文件完整骨架，4 份「不可变原文」共约 88 KB，加上 TP 表（约 17 行 × 10 列）、TC 表（约 55 行 × 13 列长文本）、3 份 QA 报告、repair-log、clarifications 全部留在历史里。每一阶段都把这些整体重放，从不落盘卸载。截图 8 的构成条可见：会话内容 88.9K、文件 42K、工具结果 28.5K。

2. **高频工具往返 × 全量重放**
   每个工具调用都是一次完整上下文重放。本次共 99 次工具调用（3.5 节），其中 `edit` 39 次、`bash` 23 次（机验脚本 15 次 + grep 核对 7 次）。截图 8 的 `bash ×29` 为时点快照，最终记录为 23 次。新版虽已把「写一条验一条」改成批量，但往返次数仍高。

3. **每次 QA 都是全新子会话并携带全量文件清单**
   `qa-expert.md` 要求每次委派附带「需读取文件清单」，通常含 7–8 个绝对路径文件（整份 PRD 773 行、前端设计文档 1304 行、TP/TC 全表、clarifications、citation-result.json）。7 个子会话各自重新注入 system prompt、briefing、原文知识链与全表；主/子会话交错还触发第六节所述的缓存失效。

4. **「3 轮修复回路 × 3 条链」的收敛机制**
   `test-expert.md` 规定材料检、TP 检、TC 检三条链各最多 3 轮「派发 → 修复 → 复检」，最多 9 次派发；加上 4 个 question 关口，天然把请求数推高。

5. **薄壳 skill 设计迫使反复开文件**
   四份原文合计约 88 KB，skill 只写步骤「只引用不复述」，正确执行就要不断打开多个文件，每次又是一次工具往返与上下文重放。机验脚本 `lib_citation.py` 的 `find_candidates()` 对每个锚点都 `os.walk` 全目录递归、无缓存，是 50 分钟里可观的 I/O 来源。

6. **潜在自派生风险**
   主 agent 的 subagent 白名单同时含 `qa-expert: allow` 与 `test-expert: allow`，配置上允许递归启动自身；本次未触发，但属于隐患。

> 说明：`.opencodenew` 相对旧版 `.opencode` 已修复「逐条锚点校验」并改为批量，但**上下文阶段化隔离**与**QA 派发收敛**两个架构级因子仍未解决，所以消耗没有下降。

## 六、压到 200 万的可行路径

目标需砍掉约 88%，必须动架构。按收益排序：

| 优先级 | 措施 | 预期收益 |
|---|---|---|
| P0 | **阶段化上下文隔离**：每阶段产物落盘，下一阶段只带「摘要 + 文件指针」，不携带 TP/TC 全表与历史工具结果；单会话峰值从 173K 压到约 60K | 最大，直接削减重放基数 |
| P0 | **批量化工具调用**：把多次 `read / edit / bash` 合并，机验一次跑完，工具往返从 ~100 次降到 ~20 次 | 直接砍掉约一半请求次数 |
| P1 | **QA 派发收敛**：7 次降到 2 次；「3 轮修复回路」改为「内部自查 + 一次性 QA 复核」；用 `resume` 复用 QA 会话而非每次新建 | 省掉重复 system prompt 注入，减少交错失效 |
| P1 | **稳定缓存前缀**：避免改动会话开头，大工具结果落盘、上下文只留摘要 | 守住命中率，配合阶段隔离 |
| P2 | **人工关口批量化**：4 个 question 合并成 1～2 次；配置超时自动取默认建议 | 缩短约 10 分钟等待，不减 token |

测算：往返从 214 次降到约 20～30 次、单次上下文从 173K 压到约 60K，缓存重放可从 1547 万降到约 120 万，加上新增输入约 50 万、输出约 26 万，总量落在 **200 万上下**。

风险提示：P0/P1 会改变现有质量保障强度（逐条机验、3 轮 QA 是刻意设计的防错机制）。建议先在一份样本上对比「收敛率」与「缺陷漏检率」，确认质量不退化后再全量切换。

## 七、关键结论

- 两千万不是「一次生成」的开销，而是**一份膨胀到 17 万的上下文被重放一百多次**的累加。
- 90.5% 的 token 是缓存重放，推动任务的真实产出不足 10%。
- 主会话独占 82.2% 的重放，是优化的第一目标。
- 50 分钟里模型只算了约 15 分钟，其余是等待人、等子会话、反复搬上下文。
- 要把 1710 万压到 200 万，靠「阶段化上下文隔离 + 批量工具调用 + QA 收敛」三刀，而非调参数。

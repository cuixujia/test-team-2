# 测试用例生成团队 Token 消耗分析报告

## 一、结论与数据

并不是"生成一次"就花掉了 2000 万 token，而是**同一个膨胀到 24 万的上下文被反复重放了 100 多次，累计出 2000 万**。截图里的 `238K / 960K` 是"某一刻的窗口占用"，账单上的 2000 万是"所有请求逐次提交的 token 总和"，两者不是一回事。

实测总计 **18,672,790 token（约 1867 万）**，与实际观察吻合。数据来源：调用记录 `资料/requests-today-2026-11-17.csv`（158 次模型请求）、会话日志 `资料/session-ses_e18c.md`（10138 行）、团队配置 `../../.opencode`。

| 来源 | Token 数 | 占比 |
|---|---:|---:|
| 缓存复用（同一上下文反复重放） | 16,891,456 | 90.5% |
| 新增输入 | 1,517,543 | 8.1% |
| 模型输出 | 263,791 | 1.4% |

按会话拆解：

| 会话 | 角色 | 请求数 | 总 Token |
|---|---|---:|---:|
| `ses_e18ccdb` | test-expert 主 agent | 103 | 15,375,284 |
| `ses_e18c8b4` | qa-expert 子会话 1 | 16 | 1,230,249 |
| `ses_e18b450` | qa-expert 子会话 2 | 17 | 1,111,688 |
| `ses_e18bea8` | qa-expert 子会话 3 | 18 | 933,685 |

主会话一个就占 82%，上下文单调上涨：

```text
09:50  15K  →  09:54  104K  →  10:02  125K  →  10:06  179K
10:15  195K  →  10:24  219K  →  10:28  238K
```

103 次请求，每次都把当时累积的全部上下文重新提交一遍，平均每次约 13.9 万，`103 × 13.9 万 ≈ 1430 万`，这就是缓存复用那 1689 万的来源。

## 二、消耗过大的原因

核心公式：

```text
缓存 token ≈ 上下文大小 × 请求次数
```

两个因子同时偏大：上下文从 15K 涨到 238K，全程请求 103 次。所以并非只有"后期"才贵——中后期每次请求都在重复提交已累积到十几万、二十几万的上下文。打个比方：不是搬一次 24 万斤的东西，而是每次都搬当时已有的全部家当，搬了 100 多次。

需要澄清的是，缓存读本身是省钱机制（单价约为新输入的 1/10），1689 万若全按新输入计费会贵 10 倍。它只是"重复提交次数太多"的结果指标，优化要砍的是上游的请求次数和上下文大小，而不是去减少缓存命中。

**四个放大环节**

1. **逐锚点机验（最直接）**：`agent/test-expert.md:45` 要求"写一条锚点、当场验一条……攒批后补验视为违规"，直接产生 `bash ×31 / 10.9K 工具结果`。31 次 bash 就是 31 次完整上下文重放，本可合并成 1–2 次。
2. **高频交叉引用**：5 个 skill 加 4 份共 96.7 KB 的"不可变原文"被反复读取（`skill ×5 / 19.6K`、`文件 77.9K`）。配置刻意"只引用不复述"，正确执行就要不停打开多个文件，每次又是一次往返。
3. **QA 修复回路与重复派发**：`test-expert.md:58-66` 规定阶段 2/4/6 都以召唤 qa-expert 开始，各带最多 3 轮修复回路。session 日志实际有 **6 次 `task` 派发**，每次都是全新子会话，重新注入 system prompt、briefing、4 份原文、workflow skill 和 TP/TC 全表，三个 QA 子会话又贡献 328 万。
4. **产物只增不减**：TP 表、TC 表、报告、briefing、实施日志全部留在会话历史里，越往后重放越贵。虽然 `test-expert.md:92/114` 写了"不重读原文"，但产物本身没有做阶段化清理。

**缓存失效：后期最贵的放大器**

最后 6 分钟连续 5 次缓存失效，特征是整段上下文被全价重建——每次新输入量约等于失效前的缓存读量，比值 1.01–1.13，合计 863,199 token：

| 时间 | 新输入 | 失效前缓存读 | 比值 |
|---|---:|---:|---:|
| 10:22:48 | 82,966 | 75,776 | 1.09 |
| 10:23:55 | 217,959 | 216,064 | 1.01 |
| 10:25:23 | 232,707 | 219,136 | 1.06 |
| 10:26:31 | 92,894 | 81,920 | 1.13 |
| 10:27:28 | 236,673 | 235,456 | 1.01 |

失效集中在主 agent 与 QA-2 交错执行的窗口，呈交替特征：QA-2 连续跑（10:22:12–10:23:50）→ 主 agent 切回即失效（10:23:55）→ 主 agent 连续跑（10:24:18–10:26:26）→ QA-2 切回即失效（10:26:31）→ QA-2 连续跑 → 主 agent 又失效（10:27:28）。另外 2 次发生在单 agent 持续活动期间，很可能是大工具结果写入改变了前缀结构。

原因有三层：一是**多 agent 会话交错**，两套 system prompt 与上下文前缀反复切换，缓存只能保留一份，谁后到谁占用；二是**空闲超时**，CSV 有 `cache_write_5m`/`cache_write_1h` 字段，主 agent 在 10:23:55 失效前挂起 381 秒（6.3 分钟），恰好越过 5 分钟 TTL；三是**后期上下文已达 21 万–23 万**，同样失效前期只损失几万，后期要损失 20 多万。

缓存的具体失效策略是平台黑盒，以上基于 token 数据与时间线推断，但"交错切换触发失效"有大量时间线支撑。

## 三、40 分钟耗时的构成

墙钟跨度 **37.5 分钟**（09:50:51 → 10:28:18），但 CSV 记录的模型自身计算只有 **8.6 分钟**。差额约 29 分钟来自：4 个人工确认关口的等待（不计 token 但计入体感）、6 次 QA 子会话串行派发、大量 `Thinking` 长推理、工具执行与调度开销。此外那 5 次缓存失效使单次耗时从约 3 秒飙到 10–26 秒。

## 四、压到 200 万的可行路径

目标需砍掉 89%，属于架构级调整，不是调参数能解决的。按收益排序：

1. **批量化机验**：把"写一条验一条"改成"整份清单攒批后一次校验"，`bash` 从 31 次降到 2 次以内，直接砍掉约 200 万缓存重放。修改 `test-expert.md:45` 和相关 skill 的锚点校验口径。
2. **阶段化上下文隔离**：每阶段结束把产物落盘，下一阶段只带"摘要 + 文件指针"，不携带 TP/TC 全表和历史工具结果，让单会话峰值从 238K 压到 60K。这是收益最大的一刀。
3. **QA 派发收敛**：6 次降到 2 次，"3 轮修复回路"改为"先内部自查、一次性交付 QA 复核"，用 `resume` 复用 QA 会话而非每次新建。同时省掉重复 system prompt 注入，并减少 agent 交错失效。
4. **稳定缓存前缀**：避免改动会话开头内容，大工具结果落盘为文件、上下文只留摘要。这与第 2 项不矛盾——保持前缀稳定是守住命中率的底线，阶段隔离是减少重复总量，两者结合才能让缓存读自然下降。

粗略测算：往返从 103 次降到 20 次、单次上下文从 238K 压到 60K，缓存复用可从 1689 万降到约 120 万，加上新增输入约 50 万、输出 26 万，总量落在 **200 万上下**。

需要注意，第 1、3 项会改变现有质量保障强度（逐条机验和 3 轮 QA 是刻意设计的防错机制），建议先在一份样本上对比"收敛率"和"缺陷漏检率"，确认质量不退化后再全量切换。

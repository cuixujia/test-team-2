**为什么降幅不如预期**：

1. **会话复用只对前几步生效**，质检和修复的 6 个 task 全部新建会话——规则写了按类复用，但主 agent 只在资料链用了 task_id，后面忘了。
2. **子 agent 用 python 全量重写文件**（你截图里看到的），单次重写把整份清单重新输出一遍，直接制造百万级输出 token。
3. **子会话上下文滚到 200K**：TC 修复会话 203K、TP 生成会话 157K，会话内容单项 139K / 89.7K。
4. **产物量本身仍大**：111 条 TC 比上次 191 条少，但仍有相当输出成本。

**按阶段归类**：

| 阶段 | 是否复用 | 说明 |
|---|---|---|
| 功能识别 → 索引构建 → 索引修复 | 复用 | 同一资料会话，#1→#2 生效 |
| 材料质检 R1 → R2 | 部分 | #3 复用了资料会话，但这是**错误复用**：材料质检是 qa-expert，资料会话是 material-expert，两者不属同类。本次材料质检只有 R1，未暴露问题 |

**发现的问题**：#3 材料质检 R1 复用了资料会话的 task_id（`ses_e128adcc8f`），而它是 qa-expert——把质检会话挂到了资料专家的会话上。这违反"按类复用"规则。原因是规则表把"资料"和"材料质检"分成两类，但主 agent 查台账时取错了行。

真正新建的只有 4 个必要会话：功能识别、TP 生成、TP 质检 R1、TC 生成、TC 质检 R1（其中功能识别后资料链复用）。其余都复用了。但**复用次数少不等于省 token**——因为复用的会话本身已经积累了 150K+ 上下文，每次追加都要重发历史。

## 三、卡点详解

### 卡点 1：子 agent 用 python 全量重写文件

你截图里的证据非常明确：

> `Rewriting everything now — but at least the fixes will be in place`
> `apply surgical edits with python3 (per-file) to keep edits minimal`

TC 修复子 agent 先用 edit 工具尝试失败（"Invalid input: expected string, received undefined"），随后改用 python 脚本全量重写 `test-case-table.md`。截图显示该会话：

| 项 | 值 |
|---|---:|
| 上下文 | 203K |
| 会话内容 | 139K（第1轮 66.7K + 第2轮 72.6K） |
| test-case-table.md | read 17.4K |
| bash | ×15，result 8.5K |

全量重写一份 111 条 TC 的 13 列表格，输出 token 以万计。子 agent 本应只输出改动的几十行，却输出整份文件。

**根因**：`test-expert.md` 的写权规则写的是"首次写骨架与表头，数据行按功能分段追加，每批 ≤60 行；同一清单多处改动一次 edit 完成"——但**没有禁止全量重写，也没有给 edit 失败时的正确退路**。模型遇到 edit 参数错误就退化成 python 重写。

### 卡点 2：会话内容滚雪球

三张上下文截图：

| 会话 | 上下文 | 会话内容 | 文件 | 工具结果 |
|---|---:|---:|---:|---:|
| TC 修复 | 203K | 139K | — | bash 8.5K |
| TP 生成 | 157K | 89.7K | 48.2K（4 份知识库原文 9K/8.7K/8.2K/5.7K） | — |
| TC 质检 | 123K | 61.9K | 37.2K（test-case-table.md 17.9K） | 17.5K |

会话复用让历史轮次不断累积。TP 生成会话读了四份知识库原文合计 31.6K——这些是一次性知识，读完就沉淀在会话里，后续每次追加都重发。

### 卡点 3：请求数仍达 170

主会话 51 轮，其中 task 13 次、write 10 次、edit 12 次、question 5 次、todowrite 3 次。子会话 6 个，请求分布（截图）：51、38、37、25、19、13。

170 请求 = 主会话 51 + 子会话约 119。要压到 100，需要子会话请求数减半——主要靠消除全量重写和减少质检往返。

## 四、优化建议

| 优先级 | 措施 | 落点 | 预期 |
|---|---|---|---|
| P0 | 禁止全量重写：修复任务必须用 edit 定点改；edit 失败时按格式重试，禁止降级为 python/write 整份重写 | `test-expert.md`【修复规则】【写权与落盘】 | 省数百万输出 token |
| P0 | 台账按类记录 task_id 并**按 subagent 类型校验**：材料质检只能取材料质检行的 id，不能取资料行 | `test-manager.md`【会话复用】 | 避免 #3 类错误复用 |
| P1 | 知识库按需加载：TP 生成只读《测试维度定义》与《通用测试规则》中命中维度的小节，不读四份全文 | `test-expert.md` 委派协议 + `test-knowledge-canon` | TP 会话文件占用 48K → 15K |
| P1 | 质检 R1 全量检视改为按锚点分段读，不整份载入 37.9K 清单 | `qa-expert.md` 委派协议 | 质检会话文件占用下降 |
| P2 | 合并 write/edit：主 agent 的 state.md 每阶段重写一次改为定点追加 | `test-manager.md`【写权与落盘】 | 主会话 edit 12 次下降 |
| P2 | 收敛阈值：产物已稳定在 35 TP/111 TC 且 R1 质检收敛，可评估是否把部分 R2 复检改为抽查 | `quality-check` | 减少 2 次 task |

## 五、目标可达性

要从 170 请求 / 12.5M token 降到 100 / 5M，最有效的三件事：

1. **禁止全量重写**——直接砍掉最大的输出 token 块，这是你截图里发现的问题，也是 P0
2. **知识库与产物按需读**——把三个子会话的文件占用从 37K–48K 降到 15K 以内
3. **修复错误复用**——材料质检用错 task_id 虽未造成当前损失，但一旦材料走两轮会污染会话

三项做到，请求数预计降到 110–120，token 降到 6–7M。要进一步压到 100/5M，需要减少质检轮次（P2）——但那会影响产物质量，需要你权衡。

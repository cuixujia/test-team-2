# optimize1 运行分析报告：卡点、根因与产物质量下降

## 结论摘要

新方案确实起了作用——请求从 270 降到 153、token 从 16M 降到 8.2M、会话从 11 个降到 6 个。但**卡点并未消失，只是换了位置**，且**产物质量下降是本次优化引入的新问题**：

| 指标 | 上次(refector) | 本次(optimize1) | 变化 |
|---|---:|---:|---:|
| 请求数 | 270 | 153 | ↓43% |
| Token | 16.1M | 8.38M | ↓48% |
| 缓存读取 | 14.77M | 7.26M | ↓51% |
| 会话数 | 11 | 6 | ↓ |
| 测试点 | 36 | 20 | **↓44%** |
| 测试用例 | 129 | 63 | **↓51%** |
| 端到端耗时 | 52.7 min | 33.2 min | ↓37% |

三次核心结论：

1. **数量下降与优化方案无关，也不是读不到原文**：两轮用户都只选了 F01、F02（已核实），TP 基数从 36 掉到 20 是生成侧自身产出变少；TC 回报明确"无覆盖缺口、warnings=0"。真正原因是**生成 prompt 里缺了展开密度约束**，唯一数值下限写成"每 TP 至少 1 条用例"。
2. **token 仍高的第一卡点是"会话内容滚雪球"**：缓存读取 7.26M 仍占 86.7%，单次请求 token 中位数 5 万、峰值 14.7 万；子会话里 `会话内容` 单项就占 55–81K。
3. **新方案没解决的两处老问题**：材料质检仍走满 R1→修复→R2 两轮；主会话出现约 166 行"先澄清还是先修复"的流程拉锯，这是纯粹的内耗。

## 二、卡点定位

### 卡点 1：子会话上下文滚雪球（最大 token 消耗）

截图显示三个子会话的上下文：`ses_e158` 已用 147K、`ses_e159` 分别 61.2K 与 106K。拆开看，`会话内容` 是绝对大头：

| 会话 | 已用上下文 | 会话内容 | 第1轮 | 第2轮及以后 | 文件 |
|---|---:|---:|---:|---:|---:|
| ses_e158（TC 生成/修复） | 147K | **81.4K** | 54.5K | 25.1K | 48.5K |
| ses_e159（材料/索引） | 106K | **55.8K** | 27.9K | 12.4K + 11K + … | 32.9K |
| ses_e159（主/编排） | 61.2K | 37.4K | 37.4K | — | 0.7K |

关键现象：**TC 生成与 TC 修复复用了同一会话（通过 task_id，已核实生效）**，会话内容累积到 81.4K。会话复用省掉的是"重新加载 skill 与文件"，但没有省掉"历史轮次在每次请求里重发"——复用越长，单次请求携带的上下文越大。这是"会话复用"这把双刃剑的代价，也是本次没有预期到的新卡点。

### 卡点 2：主会话的流程拉锯（内耗）

主会话 55 轮中，行 888–1054 约 166 行是同一件事的反复推演："材料质检 R1 未收敛有 2 个重大项，但收敛依赖关口 2 澄清，而流程要求先收敛再澄清……"。典型原文：

> 行 926：`这里有个矛盾：第 2 步要求先收敛冻结再进第 3 步澄清；但重大项的收敛又依赖关口 2 的澄清结论`
> 行 1054：`先做关口 2 两道澄清`

这段纠结发生在**主会话**（每次 thinking 计入 8.2M），最终结论"先澄清再修复"还改写了 QA 标准循环的顺序。更值得注意的是：这次主会话没有任何 `_Thinking_` 标记（我的统计为 0），说明thinking 被平台折叠或省略，但轮次时长（行 888 那一轮 25.6 秒）证明推理确实发生了——**思考成本被计入 token，却不会在转写里显现**，这也是"看起来主 agent 没干什么却耗时"的原因。

### 卡点 3：材料质检仍走满两轮（正常但有优化空间）

| 轮次 | 问题计数 | 收敛 | 修复内容 |
|---|---|---|---|
| R1（行 852–883） | 阻塞0/重大2/一般4 | N | 状态流转口径冲突（C1/C2/C3）+ 资料缺口（D1/D2/D3） |
| 修复（行 1619–1645） | — | — | 8 条概要回填澄清裁决；D1/D2/D3 选"静默生成"，索引不动 |
| R2（行 1742–1758） | 阻塞0/重大0/一般1 | Y | 对照表复检通过，收敛冻结 |

这是 QA 标准循环的必然路径（R1 有重大项就必须修复复检），与上次的原因同类——PRD 与 BRD 状态流转冲突。**不是 bug，但占了 3 次 task + 主会话大量篇幅。**

## 三、产物质量下降的根因（重点）

先排除一个错误假设：**不是范围收窄**。已核实上次与本次关口 1 用户都选了"仅 F01 F02"（上次 `session-ses_e15f.md` 行 867，本次行 581）。也不是读不到片段：TC 回报行 2297–2303 明确"20 条 TP 全部有直属用例、无覆盖缺口""逐条 M 值均 ≥2""warnings=0"。

真正的因果链如下：

```text
生成 prompt 缺展开密度约束
  → TP 生成只给"10 列结构/命名/排序"，无"展开重点项数 N"要求
  → TP 基数只有 20 条（上次 36 条）
  → TC 生成的唯一数值下限是"每个 TP 至少展开 1 条用例"
  → 子 agent 自主展开 2–4 条/TP，合计 63 条
```

具体证据：

1. **TP 生成 prompt（行 1904）无任何数量约束**：要求只写了"严格按 test-point-workflow 规范生成（依据类型、生成红线、条目命名、排序规则、10 列结构）""仅覆盖 F01/F02""澄清结论 C-01~C-06 作为权威口径""落盘后机验自检"——通篇没有"每个功能至少 N 条 TP""圈定小类每个至少 1 条 TP"这类要求。

2. **TC 生成 prompt（行 2277）下限写成 M=1**：
   > `逐条展开 TP 清单 20 条测试点，每个 TP 至少展开 1 条用例，展开数量守恒；F 编号与 TP 编号对齐 scope.md 与 TP 清单。`
   
   "展开数量守恒"是概念，没配具体数字。子 agent 实际做到 M≥2（行 2297），说明它自主加了码，但**没有任何机制要求它达到上次的展开密度**（上次 129/36≈3.58 条/TP，本次 63/20≈3.15 条/TP）。

3. **知识库 skill 只给名字、不给文件**：TP/TC prompt 的需读清单里写的是"test-knowledge-canon 知识清单（skill 名 test-knowledge-canon，按其中索引定位……）"，没有列出四份 references 文件名，也没有把 `test-point-workflow`/`test-case-workflow` 列入明确的加载清单——只在"要求1"里以"严格按……规范"提及。这削弱了知识链对展开密度的约束（展开数量守恒的具体规则正写在这两个 workflow skill 里）。

4. **澄清口径从紧**：本次 TP prompt 要求"默认标题/附件约束/受理人角色缺口按宽泛表述，不写具体格式或字段取值"（行 1904），上次方案对这些缺口的处理更放开。这也压缩了可展开的具体取值维度。

## 四、新方案各措施的实测效果

| 方案措施 | 预期 | 实测 | 结论 |
|---|---|---|---|
| 主 agent 零原文/零 skill/零产物读取 | 大幅省主会话 token | 主 agent 仅 2 次 read，均为自己写的台账；bash 5 次均非机验；verify_citation 从未作为主 agent 工具调用出现 | **达成** |
| 原文片段改回资源索引、按锚点读小片段 | 省子 agent token | 子 agent 文件占用仍 32–48K，含 PRD/FDD 等原文；但会话内容是更大头（55–81K） | 部分达成 |
| 会话复用 | 省重复加载 | 7/12 次复用带 task_id 生效 | 达成，但引入长会话滚雪球副作用 |
| QA 判据前移做自检卡 | R1 一次通过 | 材料 R1 仍 N；TP R1 直接 Y；TC R1 仍 N | 部分达成（TP 收敛，材料/TC 未） |
| 澄清题目由 QA 回报搬运 | 主 agent 不读报告 | 关口 2 两题确实取自回报；但主会话为"先澄清还是先修复"内耗 166 行 | 达成但被内耗抵消 |

## 五、下一步修改建议（按优先级）

### P0：修复产物质量下降（必须）

1. **在 `test-manager.md` 的 TP/TC 派发 prompt 模板里加入数量约束**：
   - TP 生成：`圈定小类每个至少 1 条 TP；每个选中功能的正向/反常/规则遗漏/边界维度须有落点；参考上次基线约 18 条/功能`
   - TC 生成：把"每个 TP 至少展开 1 条用例"改为"按 `test-case-workflow`【展开数量守恒】逐字段/逐约束展开；每个 TP 直属用例 M≥2（字段校验类按字段数×约束类型数核算），禁止按 TP 均摊条数"
2. **在 `test-expert.md` 委派协议里把 workflow skill 列为必加载**：明确 `test-point-workflow`、`test-case-workflow` 必须加载并以其展开数量守恒为准，而不是只在 prompt 里以"严格按……规范"一句带过。

### P1：抑制上下文滚雪球

3. **限制会话复用长度**：对同一 task_id 的连续追加设上限（如 TP 生成→TC 生成→TC 修复 3 次以内）；超过则新建会话，把前序结论摘要随 prompt 传入，而不是无限追加。
4. **主会话内不需要再把 QA 回报全文写成思考**：行 888–1054 的流程拉锯，根因是"澄清题目含重大项"与"先收敛再澄清"的顺序冲突。建议在 `test-manager.md` 阶段 2 明确写"材料 QA 的待澄清问题（含重大项）不属于需收敛的阻塞项，直接登记关口 2，收敛判定只针对索引完整性与锚点"，从规则上消除纠结。

### P2：其他

5. 材料质检 R1 的重大项多为"PRD/BRD 状态流转冲突"——可在索引构建时让 `material-expert` 对跨资料矛盾主动标记，减少 QA R1 的发现量。
